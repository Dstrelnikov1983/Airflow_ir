Параметр schedule в DAG

Определяет когда и как часто запускается DAG.

  • Cron-строка: "*/15 * * * *"
  • Timedelta: timedelta(hours=1)
  • Пресет: "@daily"
  • Объект Timetable
  • None — только вручную
Важно: schedule определяет логический интервал, а не момент запуска. DAG стартует после окончания интервала.
В Airflow 2.x параметр schedule_interval устарел — используйте schedule. 
from airflow import DAG
from datetime import datetime, timedelta

# Cron: каждые 15 минут
dag_glonass = DAG(
    dag_id="glonass_telemetry",
    schedule="*/15 * * * *",
    start_date=datetime(2024, 3, 1),
)

# Timedelta: каждый час
dag_kpi = DAG(
    dag_id="hourly_kpi",
    schedule=timedelta(hours=1),
    start_date=datetime(2024, 3, 1),
)

# Пресет: ежедневно
dag_report = DAG(
    dag_id="daily_summary",
    schedule="@daily",
    start_date=datetime(2024, 3, 1),
)

# Только вручную (нет авторасписания)
dag_manual = DAG(
    dag_id="manual_audit",
    schedule=None,
    start_date=datetime(2024, 3, 1),
)

Cron-синтаксис

ПолеДопустимые значенияСпецсимволы
Минуты0–59* , - /
Часы0–23* , - /
Дни месяца1–31* , - / ?
Месяцы1–12* , - /
Дни недели0–7 (0 и 7 = вс)* , - /

Примеры (UTC):

  • */15 * * * * — каждые 15 минут
  • 0 * * * * — каждый час
  • 0 17,1,9 * * * — 3 раза в сутки
  • 0 23 * * * — ежедневно в 23:00
  • 0 0 * * 1 — каждый понедельник в 00:00
Онлайн-проверка: crontab.guru 
from croniter import croniter
from datetime import datetime

# Проверка расписания смен ТЧЭ-15 (UTC)
cron = croniter(
    "0 17,1,9 * * *",
    datetime(2024, 3, 1)
)

# Вывод следующих 6 запусков
print("Следующие запуски (UTC):")
for i in range(6):
    nxt = cron.get_next(datetime)
    print(f"  {nxt.strftime('%Y-%m-%d %H:%M')}")

# Вывод:
# 2024-03-01 09:00  (смена 3 → 16:00 НСК)
# 2024-03-01 17:00  (смена 1 → 00:00 НСК)
# 2024-03-02 01:00  (смена 2 → 08:00 НСК)
# 2024-03-02 09:00  (смена 3 → 16:00 НСК)
# 2024-03-02 17:00  (смена 1 → 00:00 НСК)
# 2024-03-03 01:00  (смена 2 → 08:00 НСК)
Совет: Всегда проверяйте cron-выражение перед деплоем. Ошибка в расписании = пропущенные или лишние запуски DAG.

Параметр start_date

Определяет начало логического календаря DAG.

Ключевое правило:
Первый DAG Run стартует не в момент start_date, а после завершения первого полного интервала.
Пример: start_date=2024-03-01, schedule="@daily"
Первый run: 2024-03-02 00:00
data_interval_start = 2024-03-01 00:00
data_interval_end = 2024-03-02 00:00

Правила:

  • Всегда задавать статическую дату
  • Не использовать datetime.now()
  • Предпочтительно: pendulum.datetime()
import pendulum
from airflow import DAG

# Правильно: статическая дата с TZ
dag_shift = DAG(
    dag_id="shift_report",
    schedule="0 17,1,9 * * *",
    start_date=pendulum.datetime(
        2024, 3, 1,
        tz="Asia/Novosibirsk"
    ),
    catchup=False,
)

# НЕПРАВИЛЬНО — не делайте так!
# start_date=datetime.now()
# start_date=datetime.today()
#
# При каждом перечтении DAG-файла
# start_date будет меняться.
# Это нарушает логику catchup:
# scheduler не может понять,
# за какие периоды уже были runs.

# Рекомендация для ТЧЭ-15:
# start_date = дата первого запуска
# аналитической платформы в деп
# (например, 2024-03-01)
Антипаттерн: datetime.now()
Лучшая практика: pendulum

catchup и операция backfill

catchup

Автоматическое наверстывание пропущенных интервалов.

ЗначениеПоведение
True (умолч.) Создаёт runs за все пропущенные периоды
False Создаёт только последний run
Риск: DAG с расписанием каждые 15 минут и catchup=True после 5 дней простоя создаст 480 runs (5 сут × 24 ч × 4 запуска/ч).

backfill — ручное восстановление

airflow dags backfill \
    --dag-id shift_adherence_report \
    --start-date 2024-03-01 \
    --end-date 2024-03-07 \
    --reset-dagruns
from airflow import DAG
import pendulum
from datetime import timedelta

NSK = "Asia/Novosibirsk"

# Телеметрия ГЛОНАСС: catchup=False
# Реальное время — прошлое не нужно
glonass_dag = DAG(
    dag_id="glonass_telemetry",
    schedule="*/15 * * * *",
    start_date=pendulum.datetime(
        2024, 3, 1, tz=NSK
    ),
    catchup=False,      # ← важно!
    max_active_runs=1,
    dagrun_timeout=timedelta(minutes=10),
)

# Посменный отчёт: catchup=True
# Нужно восстановить пропущенные смены
shift_dag = DAG(
    dag_id="shift_adherence_report",
    schedule="0 17,1,9 * * *",
    start_date=pendulum.datetime(
        2024, 3, 1, tz=NSK
    ),
    catchup=True,       # ← восстанавливаем
    max_active_runs=3,  # до 3 смен параллельно
)

max_active_runs и параллелизм

Ограничивает число одновременно активных DAG Run для одного DAG.

По умолчанию: значение из airflow.cfg
(max_active_runs_per_dag = 16)

Типовые рекомендации:

Тип DAGmax_active_runsПричина
Потоковый (15 мин)1Не накапливать очередь
Почасовой (1 ч)2Небольшой параллелизм
Периодический отчёт3Несколько периодов сразу
Ежедневная сводка1Строгий порядок
Еженедельный отчёт1Один раз в неделю
При catchup-восстановлении временно увеличьте max_active_runs, затем верните обратно. 
from airflow import DAG
import pendulum
from datetime import timedelta

# Телеметрия: строго один run за раз
glonass_dag = DAG(
    dag_id="glonass_telemetry",
    schedule="*/15 * * * *",
    start_date=pendulum.datetime(
        2024, 3, 1,
        tz="Asia/Novosibirsk"
    ),
    catchup=False,
    max_active_runs=1,
    # Если DAG завис — освободить слот
    dagrun_timeout=timedelta(minutes=10),
)

# Пул ресурсов для телеметрии
default_args = {
    "pool": "rzd_telemetry_pool",
    "pool_slots": 1,
    "priority_weight": 10,
    "retries": 2,
    "retry_delay": timedelta(minutes=1),
}
Разница:
max_active_runs — уровень DAG (кол-во одновременных запусков DAG)
concurrency в airflow.cfg — глобальный лимит задач

Временные зоны в Airflow

Airflow хранит все метки времени в UTC!
Для локального часового пояса UTC+7 это критично: событие в 08:00 местного времени = 01:00 UTC.

Примеры часовых поясов:

РегионЗонаСмещение
НовосибирскAsia/NovosibirskUTC+7
МоскваEurope/MoscowUTC+3
Airflow DBUTCUTC+0

Локальное время в разных зонах:

ТочкаМестное (UTC+7)UTC
Точка 100:0017:00 пред. дня
Точка 208:0001:00
Точка 316:0009:00
 
import pendulum
from airflow import DAG

# Явное указание TZ в start_date
NSK_TZ = pendulum.timezone(
    "Asia/Novosibirsk"
)

# Смены 00:00, 08:00, 16:00 НСК
# = 17:00, 01:00, 09:00 UTC
shift_dag = DAG(
    dag_id="shift_report_nsk",
    # Cron ВСЕГДА в UTC для Airflow!
    schedule="0 17,1,9 * * *",
    start_date=pendulum.datetime(
        2024, 3, 1, tz=NSK_TZ
    ),
    catchup=False,
)

# Сводка для руководства в 06:00 НСК
# 06:00 НСК = 23:00 UTC (пред. день)
mgmt_dag = DAG(
    dag_id="daily_management_report",
    schedule="0 23 * * *",  # UTC
    start_date=pendulum.datetime(
        2024, 3, 1, tz=NSK_TZ
    ),
    catchup=False,
)
pendulum встроен в Airflow и автоматически обрабатывает переходы часовых поясов и летнее время.

Кастомные Timetables

Позволяют задать произвольную логику расписания, которую нельзя выразить cron-строкой.

Типовые сценарии:

  • Запуск только в рабочие дни (с учётом производственного календаря)
  • Расписание по внешнему нормативному графику
  • Адаптивный запуск по завершению периода (не по фиксированному часу)
  • Отчёт после закрытия учётного периода
  • Пропуск ежедневного окна обслуживания (02:00–04:00)
Timetable — Python-класс, реализующий интерфейс из airflow.timetables.base.
Регистрируется как Airflow plugin. 
from airflow.timetables.base import (
    DagRunInfo, DataInterval,
    TimeRestriction, Timetable
)
import pendulum

class ShiftTimetable(Timetable):
    """Расписание 3 смен ТЧЭ-15 (НСК)."""
    # Начало смен в НСК
    SHIFT_HOURS = [0, 8, 16]
    TZ = pendulum.timezone(
        "Asia/Novosibirsk"
    )

    def next_dagrun_info(
        self,
        last_automated_data_interval,
        restriction: TimeRestriction,
    ):
        now = pendulum.now(self.TZ)
        for h in self.SHIFT_HOURS:
            candidate = now.set(
                hour=h, minute=5,
                second=0, microsecond=0
            )
            if candidate > now:
                return DagRunInfo.interval(
                    start=candidate,
                    end=candidate.add(hours=8)
                )
        # Первая смена следующих суток
        nxt = now.add(days=1).set(
            hour=0, minute=5,
            second=0, microsecond=0
        )
        return DagRunInfo.interval(
            start=nxt,
            end=nxt.add(hours=8)
        )

Код: Расписания пайплайнов ТЧЭ-15

# Различные варианты расписания для РЖД-пайплайнов
from airflow import DAG
from datetime import timedelta
import pendulum

NSK_TZ = pendulum.timezone("Asia/Novosibirsk")

# Каждые 15 минут — телеметрия ГЛОНАСС локомотивов ТЧЭ-15
glonass_dag = DAG(
    dag_id="glonass_telemetry",
    schedule="*/15 * * * *",
    start_date=pendulum.datetime(2024, 3, 1, tz=NSK_TZ),
    catchup=False,           # не восстанавливать прошлое
    max_active_runs=1,       # один run за раз
    dagrun_timeout=timedelta(minutes=10),
    tags=["telemetry", "realtime", "tche15"],
)

# Каждый час — расчёт KPI: температура букс, тяговый ток
buxa_kpi = DAG(
    dag_id="buxa_kpi_hourly",
    schedule="0 * * * *",   # в начале каждого часа (UTC)
    start_date=pendulum.datetime(2024, 3, 1, tz=NSK_TZ),
    catchup=False,
    tags=["kpi", "safety", "tche15"],
)

# Каждые 8 часов — посменный отчёт (смены: 0, 8, 16 НСК = 17, 1, 9 UTC)
shift_report = DAG(
    dag_id="shift_adherence_report",
    schedule="0 17,1,9 * * *",
    start_date=pendulum.datetime(2024, 3, 1, tz=NSK_TZ),
    catchup=True,            # восстанавливаем пропущенные смены
    max_active_runs=3,       # до 3 смен параллельно
    tags=["report", "schedule", "tche15"],
)

# Ежедневно в 06:00 НСК — сводка для руководства дирекции тяги
daily_summary = DAG(
    dag_id="daily_management_report",
    schedule="0 23 * * *",  # UTC: 23:00 = 06:00 следующего дня НСК
    start_date=pendulum.datetime(2024, 3, 1, tz=NSK_TZ),
    catchup=False,
    tags=["report", "management", "tche15"],
)

# Каждый понедельник в 07:00 НСК — недельный OTD-отчёт по грузовым перевозкам
weekly_report = DAG(
    dag_id="weekly_otd_report",
    schedule="0 0 * * 1",   # UTC: 00:00 пн = 07:00 пн НСК
    start_date=pendulum.datetime(2024, 3, 1, tz=NSK_TZ),
    catchup=True,
    tags=["report", "otd", "weekly", "tche15"],
)

Вопрос для обсуждения

Обсудите в группе (5 мин):

Airflow-сервер ТЧЭ-15 был остановлен на 5 суток для планового технического обслуживания.

После запуска все DAG с catchup=True начали наверстывать упущенное.

Вопросы:
  1. Сколько DAG runs создастся для glonass_telemetry (*/15 * * * *)?
  2. Сколько для shift_adherence_report (3 раза в сутки)?
  3. Каковы последствия для сервера и базы данных PostgreSQL?
  4. Как нужно было настроить DAG, чтобы избежать этой ситуации?
Подсказка: 5 сут × 24 ч × 4 = 480 runs для ГЛОНАСС, 5 × 3 = 15 runs для посменного отчёта.
Решение: catchup=False + max_active_runs=1 + dagrun_timeout.

Кейс: Перегрузка Airflow после обслуживания

Ситуация:
Airflow-сервер ТЧЭ-15 был остановлен на 5 дней для планового обслуживания. После запуска все DAG с catchup=True начали наверстывать упущенное — это создало 120+ одновременных runs. Сервер перестал отвечать, PostgreSQL получил пиковую нагрузку, несколько runs упали с timeout. Руководство дирекции тяги не получило утреннюю сводку.

Что пошло не так:

  • Проблема 1: catchup=True для DAG реального времени (телеметрия)
  • Проблема 2: Нет max_active_runs — все runs стартовали одновременно
  • Проблема 3: Нет dagrun_timeout — зависшие runs не освобождали ресурсы
  • Проблема 4: Нет приоритетов — критичные DAG встали в общую очередь

Как исправить:

  • Решение 1: catchup=False для телеметрии и KPI-DAG
  • Решение 2: max_active_runs=1 — последовательное наверстывание
  • Решение 3: dagrun_timeout=timedelta(minutes=30)
  • Решение 4: priority_weight — приоритет критичных DAG выше

Ключевые понятия:

  • schedule — cron / timedelta / пресет / Timetable

  • catchup=True/False — управление наверстыванием пропусков

  • Пресеты: @daily, @hourly, @weekly — удобны, но ограничены
