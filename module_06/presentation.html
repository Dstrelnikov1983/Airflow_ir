Условное выполнение в ETL-пайплайнах

Реальность производственных данных

  • Данные не всегда одинаковые — записи бывают валидными и невалидными
  • Процесс переходит в разные режимы: нормальный, предупреждение, ошибка
  • Некоторые задачи нужно выполнять только при определённых условиях
  • Лишние вычисления = потраченные ресурсы облака
Принцип: DAG должен реагировать на данные, а не просто выполнять фиксированный сценарий.

Типичные примеры условий

Проверка качества данных
Метрика < порога → отправить алерт
Метрика ≥ порога → стандартная обработка
Состояние объекта
Значение > порога → создать заявку
Норма → пропустить создание заявки
Данные за период есть?
Нет данных → остановить расчёт метрик
Есть данные → рассчитать показатели

BranchPythonOperator

Механизм работы

  • Принимает Python-функцию как аргумент python_callable
  • Функция возвращает task_id (строку) или список task_id
  • Airflow запускает только указанные задачи
  • Остальные задачи получают статус SKIPPED
  • Нижестоящие задачи (downstream) тоже пропускаются
⚠️ Важно: Задача, объединяющая ветки (join), должна иметь trigger_rule="none_failed_min_one_success" или "one_success"

Что возвращает функция

Одна ветка:
return "task_alert"
Несколько веток:
return ["task_alert", "task_log"]
Динамический выбор:
return branches[status]
Статус задачиЗначение
SUCCESSВыбранная ветка выполнена
SKIPPEDНе выбранные ветки

BranchPythonOperator: качество руды


from airflow import DAG
from airflow.operators.python import BranchPythonOperator, PythonOperator
from airflow.operators.empty import EmptyOperator
from datetime import datetime

def check_ore_quality(**context):
    """Ветвление по содержанию железа (Fe%) в руде."""
    # Получаем показатель Fe% из XCom предыдущей задачи
    fe_percent = context["ti"].xcom_pull(task_ids="extract_ore_data", key="fe_percent")

    if fe_percent is None:
        # Данные не получены — останавливаем поток
        return "no_data_alert"
    elif fe_percent < 55.0:
        # Критически низкое содержание Fe — авария
        return "critical_alert_branch"
    elif fe_percent < 60.0:
        # Пониженное содержание Fe — предупреждение
        return "warning_alert_branch"
    else:
        # Нормальное качество руды
        return "normal_processing"

with DAG("ore_quality_branch", start_date=datetime(2024, 1, 1), schedule="@hourly") as dag:

    extract_data    = PythonOperator(task_id="extract_ore_data",    python_callable=lambda: None)
    branch          = BranchPythonOperator(task_id="quality_branch", python_callable=check_ore_quality)
    normal_proc     = PythonOperator(task_id="normal_processing",   python_callable=lambda: None)
    warning_alert   = PythonOperator(task_id="warning_alert_branch", python_callable=lambda: None)
    critical_alert  = PythonOperator(task_id="critical_alert_branch", python_callable=lambda: None)
    no_data_alert   = PythonOperator(task_id="no_data_alert",       python_callable=lambda: None)
    finalize        = EmptyOperator(task_id="finalize",
                                    trigger_rule="none_failed_min_one_success")

    extract_data >> branch >> [normal_proc, warning_alert, critical_alert, no_data_alert]
    [normal_proc, warning_alert, critical_alert, no_data_alert] >> finalize
Fe% ≥ 60 → normal_processing Fe% 55–60 → warning_alert_branch Fe% < 55 → critical_alert_branch нет данных → no_data_alert

ShortCircuitOperator

Когда использовать

  • Когда нужно полностью остановить все нижестоящие задачи
  • Нет «ветки-альтернативы» — только «продолжить» или «стоп»
  • Python-функция возвращает True или False
  • При False — все downstream-задачи получают SKIPPED
  • Параметр ignore_downstream_trigger_rules управляет поведением
Отличие от Branch: ShortCircuit не выбирает между вариантами — он просто «отключает» весь остальной DAG.

Пример: проверка наличия данных


from airflow.operators.python import ShortCircuitOperator

def shift_data_exists(**context):
    """
    Проверяем, есть ли данные
    за текущую смену из шахты.
    Если нет — останавливаем DAG.
    """
    shift_id = context["ti"].xcom_pull(
        task_ids="get_shift_info",
        key="shift_id"
    )
    records = query_db(shift_id)
    return len(records) > 0

check_shift = ShortCircuitOperator(
    task_id="check_shift_data",
    python_callable=shift_data_exists,
    ignore_downstream_trigger_rules=False,
)
True → расчёт метрик, отчёты, загрузка в хранилище
False → все задачи SKIPPED, DAG завершён

TaskGroup: организация сложных DAG

Что даёт TaskGroup

  • Логическая группировка связанных задач
  • Визуальное сворачивание в Airflow UI
  • Позволяет задавать зависимости между группами, а не между отдельными задачами
  • Поддерживаются вложенные TaskGroup
  • Уникальный group_id — задачи внутри именуются group_id.task_id
Без TaskGroup: DAG с 30+ задачами превращается в нечитаемую «макаронину». TaskGroup наводит порядок.

TaskGroup: код для Руда+


from airflow import DAG
from airflow.operators.python import PythonOperator
from airflow.utils.task_group import TaskGroup
from datetime import datetime

with DAG("ore_taskgroup_demo", start_date=datetime(2024, 1, 1), schedule="@daily") as dag:

    # ── Группа 1: Сбор данных ──────────────────────────────────────────
    with TaskGroup(group_id="data_collection") as tg_collect:
        read_sensors = PythonOperator(task_id="read_sensors",    python_callable=lambda: None)
        read_gps     = PythonOperator(task_id="read_gps",        python_callable=lambda: None)
        read_video   = PythonOperator(task_id="read_video",      python_callable=lambda: None)

    # ── Группа 2: Анализ качества ─────────────────────────────────────
    with TaskGroup(group_id="quality_analysis") as tg_quality:
        validate_fe   = PythonOperator(task_id="validate_fe",   python_callable=lambda: None)
        calc_moisture = PythonOperator(task_id="calc_moisture",  python_callable=lambda: None)
        calc_sulfur   = PythonOperator(task_id="calc_sulfur",   python_callable=lambda: None)
        # Внутри группы: validate_fe первым
        validate_fe >> [calc_moisture, calc_sulfur]

    # ── Группа 3: Отчётность ──────────────────────────────────────────
    with TaskGroup(group_id="reporting") as tg_report:

        # Вложенная группа для уведомлений
        with TaskGroup(group_id="notifications") as tg_notify:
            send_email = PythonOperator(task_id="send_email",  python_callable=lambda: None)
            send_sms   = PythonOperator(task_id="send_sms",    python_callable=lambda: None)

        gen_report = PythonOperator(task_id="gen_report", python_callable=lambda: None)
        gen_report >> tg_notify

    # ── Зависимости между группами ────────────────────────────────────
    tg_collect >> tg_quality >> tg_report
data_collection.read_sensors quality_analysis.validate_fe reporting.notifications.send_email

Dynamic Task Mapping

Проблема без динамического маппирования

12 однотипных объектов — 12 одинаковых задач?

process_item_1 >> store_1
process_item_2 >> store_2
process_item_3 >> store_3
... (и так 12 раз)
⚠️ Код дублируется, трудно поддерживать, добавление нового объекта требует правки DAG

Решение: expand()

  • Задача создаётся динамически для каждого элемента списка
  • Список определяется во время выполнения (runtime)
  • Задачи выполняются параллельно
  • Доступно с Airflow 2.3+

Как работает expand()

process_item.expand(item=[...])
▼
Элемент-1
Элемент-2
Элемент-3
▼ ▼ ▼
store_results (XCom list)
Каждая mapped-задача получает свой элемент через параметр и выполняется в отдельном worker-процессе

expand(): параллельная обработка элементов


from airflow import DAG
from airflow.decorators import task
from datetime import datetime

MINE_SECTIONS = ["Блок-1", "Блок-2", "Блок-3"]

with DAG("mine_sections_expand", start_date=datetime(2024, 1, 1), schedule="@hourly") as dag:

    @task
    def get_sections() -> list[str]:
        """Возвращает список активных участков из БД."""
        # В реальной задаче — запрос к MES-системе
        return ["Блок-1", "Блок-2", "Блок-3"]

    @task
    def process_section(section: str) -> dict:
        """
        Обрабатывает данные одного участка шахты.
        Вызывается параллельно для каждого section.
        """
        print(f"Обработка участка: {section}")
        # Читаем данные датчиков, считаем KPI
        ore_volume   = read_ore_volume(section)
        fe_percent   = read_fe_percent(section)
        machine_oee  = calc_oee(section)
        return {
            "section": section,
            "ore_volume": ore_volume,
            "fe_percent": fe_percent,
            "oee": machine_oee,
        }

    @task
    def aggregate_results(results: list[dict]) -> None:
        """Собирает результаты всех участков и загружает в MES."""
        for r in results:
            print(f"{r['section']}: Fe={r['fe_percent']}%, OEE={r['oee']}%")
        save_to_mes(results)

    # Динамическое маппирование: process_section запустится 3 раза параллельно
    sections  = get_sections()
    processed = process_section.expand(section=sections)
    aggregate_results(processed)
expand(section=sections) 3 задачи параллельно результаты собираются в список

partial() + expand(): гибкое маппирование

Зачем нужен partial()

  • Часть аргументов задачи — фиксированные (одинаковы для всех)
  • Другая часть — динамические (разные для каждого элемента)
  • partial() фиксирует неизменяемые аргументы
  • expand() перебирает динамические
Аналогия: partial — это «шаблон», expand — это «цикл по данным»

Код: расчёт KPI с фиксированным порогом


from airflow.decorators import task

@task
def calc_kpi(
    section: str,
    fe_threshold: float,
    shift: str,
) -> dict:
    """
    Фиксированные: fe_threshold, shift
    Динамический: section
    """
    data = read_section_data(section, shift)
    status = "OK" if data["fe"] >= fe_threshold else "WARN"
    return {"section": section, "status": status}

sections = ["Блок-1", "Блок-2", "Блок-3"]

# partial() фиксирует общие параметры
# expand() задаёт разные section для каждой копии
results = calc_kpi.partial(
    fe_threshold=60.0,
    shift="day",
).expand(section=sections)
⚠️ Ограничение: все аргументы expand() должны быть сериализуемы (JSON). Объекты, классы, lambda — не поддерживаются.

ore_processing_flow.py — полный DAG


from airflow import DAG
from airflow.decorators import task
from airflow.operators.python import BranchPythonOperator
from airflow.operators.empty import EmptyOperator
from airflow.utils.task_group import TaskGroup
from datetime import datetime

def branch_by_quality(**context):
    fe = context["ti"].xcom_pull(task_ids="collect_data", key="avg_fe_percent")
    if fe is None:   return "no_data_alert"
    if fe < 55.0:   return "critical_alert"
    if fe < 60.0:   return "warning_alert"
    return "normal_processing"

with DAG("ore_processing_flow", start_date=datetime(2024, 1, 1),
         schedule="@hourly", catchup=False) as dag:

    @task
    def get_sections() -> list[str]:
        return ["Блок-1", "Блок-2", "Блок-3"]

    # --- TaskGroup: сбор данных (expand по участкам) ------------------
    with TaskGroup("data_collection") as tg_collect:
        @task
        def collect_data(section: str) -> dict:
            fe = read_sensors(section)
            context_obj = get_airflow_context()
            context_obj["ti"].xcom_push(key="avg_fe_percent", value=fe)
            return {"section": section, "fe": fe}

        collected = collect_data.expand(section=get_sections())

    # --- Ветвление по качеству ----------------------------------------
    quality_check = BranchPythonOperator(
        task_id="quality_branch",
        python_callable=branch_by_quality,
    )

    normal_proc    = EmptyOperator(task_id="normal_processing")
    warning_alert  = EmptyOperator(task_id="warning_alert")
    critical_alert = EmptyOperator(task_id="critical_alert")
    no_data_alert  = EmptyOperator(task_id="no_data_alert")

    finalize = EmptyOperator(
        task_id="finalize",
        trigger_rule="none_failed_min_one_success",
    )

    # --- TaskGroup: отчётность ----------------------------------------
    with TaskGroup("reporting") as tg_report:
        @task
        def gen_report(): pass
        @task
        def send_notifications(): pass
        gen_report() >> send_notifications()

    # --- Зависимости --------------------------------------------------
    tg_collect >> quality_check
    quality_check >> [normal_proc, warning_alert, critical_alert, no_data_alert]
    [normal_proc, warning_alert, critical_alert, no_data_alert] >> finalize
    finalize >> tg_report

Кейс: 12 ПДМ, параллельный расчёт KPI

Ситуация: В шахте предприятия «Руда+» работают 12 погрузочно-доставочных машин (ПДМ). Каждый час нужно рассчитывать KPI для каждой машины: OEE, часовая производительность (т/ч), расход топлива. Как избежать написания 12 одинаковых задач в DAG?

❌ Плохой подход


calc_pdm_1  = PythonOperator(task_id="calc_pdm_1",  ...)
calc_pdm_2  = PythonOperator(task_id="calc_pdm_2",  ...)
# ... ещё 10 строк ...
calc_pdm_12 = PythonOperator(task_id="calc_pdm_12", ...)
  • Дублирование кода × 12
  • Добавление ПДМ-13 = правка DAG
  • Трудно поддерживать

✅ Правильный подход: expand()


@task
def get_active_pdm() -> list[str]:
    return query_active_machines()  # из БД

@task
def calc_pdm_kpi(machine_id: str) -> dict:
    oee  = calc_oee(machine_id)
    prod = calc_productivity(machine_id)
    fuel = calc_fuel(machine_id)
    return {"id": machine_id, "oee": oee,
            "productivity": prod, "fuel": fuel}

machines = get_active_pdm()
kpi_list = calc_pdm_kpi.expand(machine_id=machines)

❓ Вопрос для обсуждения 1

Как BranchPythonOperator влияет на статус пропущенных задач? Это проблема?

Что происходит со SKIPPED-задачами

  • Задачи, которые не были выбраны ветвлением, получают статус SKIPPED
  • SKIPPED — не ошибка, но влияет на downstream-задачи
  • Задача с trigger_rule="all_success" (дефолт) тоже станет SKIPPED
  • Это не баг, а задуманное поведение Airflow

Как это решить

trigger_rule="none_failed_min_one_success"
Задача запустится, если хотя бы одна вышестоящая успешна и ни одна не упала
trigger_rule="one_success"
Запускается, как только одна вышестоящая задача успешна

❓ Вопрос для обсуждения 2

Dynamic Task Mapping — в чём ограничения при работе с большим числом элементов?
Масштаб
  • Каждый mapped-экземпляр — отдельная задача в БД Airflow
  • При expand(1000+) растёт нагрузка на metadata DB
  • Параметр max_map_length=1024 (дефолт)
Производительность
  • Слишком много параллельных задач = перегрузка workers
  • Нужно настраивать pool и max_active_tasks
  • Мониторить очереди в Celery/Kubernetes
XCom и данные
  • XCom хранится в metadata DB (ограничение размера)
  • Большие данные → использовать S3/Object Storage
  • Результаты expand собираются в список через XCom
💬 Для обсуждения: Как бы вы организовали обработку данных с 500+ датчиков в шахте через Dynamic Task Mapping? Какие ограничения нужно учесть?
Совет для Руда+: Группируйте датчики по участкам (3–5 участков), а внутри участка обрабатывайте все датчики в одной задаче. Это баланс между параллелизмом и нагрузкой.

Задача: Спроектировать поток обработки данных для 3 участков шахты с ветвлением по типам аномалий на оборудовании.

Условия задания (15 минут)

  1. Данные собираются со всех трёх участков (expand)
  2. Для каждого участка проверяется вибрация ПДМ (BranchPythonOperator):
    • Вибрация < 5 мм/с → норма → расчёт KPI
    • 5–10 мм/с → предупреждение → уведомление механику
    • > 10 мм/с → критично → остановить машину + уведомление
  3. Все задачи сбора данных объединены в TaskGroup
  4. Итоговый отчёт формируется независимо от результата ветвления
Подсказка: Нарисуйте схему DAG на бумаге до написания кода. Определите trigger_rule для финального узла.

Результат работы группы

1. Схема DAG
Нарисовать граф с узлами и ветками (можно на доске или в draw.io)
2. Псевдокод
Написать структуру DAG: TaskGroup, Branch, expand — без деталей реализации
3. Презентация (3 мин)
Каждая группа рассказывает о своём решении, объясняет выбор trigger_rule
Группа 1: Блок-1, Блок-2, Блок-3 Группа 2: Ствол-Север, Ствол-Юг + 1 блок
