Jinja2 в Apache Airflow

Jinja2 — движок шаблонов, встроенный в Airflow. Позволяет вставлять динамические значения в параметры операторов.

  • Шаблон вычисляется в момент выполнения задачи, а не при разборе DAG
  • Работает в полях: sql, bash_command, op_kwargs и др.
  • Синтаксис: {{ переменная }} и {% if ... %}
Вопрос: Почему важно, что шаблон вычисляется при выполнении, а не при загрузке DAG?

Пример

-- Без шаблона (жёсткая дата — проблема!)
SELECT *
FROM rzd_analytics.fuel_consumption
WHERE shift_date = '2024-03-15';

-- С Jinja2 (дата подставляется автоматически)
SELECT
    loco_id,
    SUM(fuel_liters) AS liters,
    SUM(distance_km) AS km
FROM rzd_analytics.fuel_consumption
WHERE shift_date = '{{ ds }}'
GROUP BY loco_id;

Результат: DAG всегда анализирует свою дату выполнения.

Покажите разницу на доске: статичная дата vs шаблон. Ключевой момент: при catchup=True Airflow «догоняет» пропущенные даты — без шаблона все запросы читали бы одну и ту же дату.

Макросы дат в Airflow

Для execution_date = 2024-03-15 08:00:00 UTC:

Макрос Значение Применение
{{ ds }} 2024-03-15 Дата обрабатываемого интервала
{{ ts }} 2024-03-15T08:00:00+00:00 Временная метка события
{{ prev_ds }} 2024-03-14 Сравнение показателей день-к-дню
{{ next_ds }} 2024-03-16 Расчёт на следующий период
{{ ds_nodash }} 20240315 Имя файла: report_20240315.csv
{{ execution_date }} объект pendulum.DateTime Доступ к компонентам даты (.hour)
В Airflow 2.2+ execution_date устарел. Рекомендуется data_interval_start / data_interval_end или параметры ds / ts в функциях задач.
Попросите аудиторию назвать ещё пример, где prev_ds пригодится. Ответ: сравнение задержек поездов вчера и сегодня; расход топлива за предыдущую смену.

Макросы дат: SQL для ТЧЭ-15

Расход электроэнергии за смену

SELECT
    l.series,
    l.number,
    SUM(ec.energy_kwh)   AS total_kwh,
    SUM(ec.distance_km)  AS total_km,
    ROUND(
        SUM(ec.energy_kwh)
        / NULLIF(SUM(ec.distance_km), 0),
        2
    ) AS kwh_per_km
FROM rzd_analytics.energy_consumption ec
JOIN rzd_analytics.locomotives l
    ON l.loco_id = ec.loco_id
WHERE ec.shift_date = '{{ ds }}'
  AND l.traction_type = 'electric'
GROUP BY l.series, l.number
ORDER BY kwh_per_km DESC;

Сравнение топлива: день к дню

SELECT
    loco_id,
    SUM(CASE WHEN shift_date = '{{ ds }}'
             THEN fuel_liters ELSE 0 END)
        AS today_liters,
    SUM(CASE WHEN shift_date = '{{ prev_ds }}'
             THEN fuel_liters ELSE 0 END)
        AS yesterday_liters,
    SUM(CASE WHEN shift_date = '{{ ds }}'
             THEN fuel_liters ELSE 0 END)
    - SUM(CASE WHEN shift_date = '{{ prev_ds }}'
               THEN fuel_liters ELSE 0 END)
        AS delta_liters
FROM rzd_analytics.fuel_consumption
WHERE shift_date IN ('{{ ds }}', '{{ prev_ds }}')
GROUP BY loco_id;
Спросите: «Как изменится запрос, если нужно сравнить не день, а смену?» Направьте к использованию execution_date.hour для вычисления номера смены (1, 2, 3).

Airflow Variables — конфигурация без деплоя

Что такое Variables?

  • Хранилище пар ключ-значение в базе Airflow
  • Управляются через UI, CLI или REST API
  • Не требуют деплоя при изменении значений
  • Могут хранить JSON-объекты
  • Значения шифруются в Fernet при AIRFLOW__CORE__FERNET_KEY

Variables: пример конфигурации

КлючЗначение
depot_code TCH-15
axle_temp_critical80
fuel_norm_lh 45.0
otd_threshold_pct95
active_locos ["VL80S-1234","2TE116-567"]

Использование в Python

from airflow.models import Variable
import json

# Простое строковое значение
depot = Variable.get(
    "depot_code",
    default_var="TCH-15"
)

# Числовое значение (тип — всегда str, нужно преобразовать)
crit_temp = float(Variable.get(
    "axle_temp_critical",
    default_var=80
))

# JSON-значение
locos = json.loads(Variable.get(
    "active_locos",
    default_var="[]"
))
# -> ["VL80S-1234", "2TE116-567"]

# В шаблоне Jinja2 (в параметрах оператора):
# {{ var.value.depot_code }}
# {{ var.json.active_locos }}
Объясните: Variables — «конфигурационный файл» для DAG. Покажите в UI Airflow (Admin → Variables), как создать переменную вручную. Важно: каждый Variable.get() — это запрос к БД; кешируйте значения в переменные Python.

dag_run.conf — запуск DAG с параметрами

Назначение

  • Передача произвольных параметров при ручном запуске DAG
  • Доступны через {{ dag_run.conf }} в шаблонах
  • Или через context["dag_run"].conf в Python
  • Полезны для разовых аналитических запросов

Запуск через Airflow UI

Trigger DAG → Configuration JSON: 
{
  "start_date":  "2024-01-01",
  "end_date":    "2024-03-31",
  "depot_code":  "TCH-15",
  "loco_series": "VL80S"
}

Использование в DAG (TaskFlow)

@task
def extract_period_data(**context):
    conf  = context["dag_run"].conf or {}

    start  = conf.get("start_date", context["ds"])
    end    = conf.get("end_date",   context["ds"])
    depot  = conf.get(
        "depot_code",
        Variable.get("depot_code", "TCH-15")
    )
    series = conf.get("loco_series", "%")

    sql = f"""
        SELECT
            loco_id,
            SUM(fuel_liters) AS total_fuel
        FROM rzd_analytics.fuel_consumption
        WHERE shift_date
              BETWEEN '{start}' AND '{end}'
          AND depot_code  = '{depot}'
          AND loco_series LIKE '{series}'
        GROUP BY loco_id
    """
    return {"sql": sql, "start": start, "end": end}
Покажите диалог «Trigger DAG w/ config» в Airflow UI. Спросите: «Для каких задач аналитики это удобнее, чем жёсткое расписание?» Ответ: квартальные отчёты, расследование инцидентов, внеплановые проверки.

XCom — обмен данными между задачами

Принцип работы

  • XCom (Cross-Communication) — механизм передачи небольших значений между задачами одного DAG Run
  • Хранится в метаданных Airflow (таблица xcom в PostgreSQL)
  • Ограничение: только малые объёмы (< нескольких МБ)
  • Для больших данных — передавайте путь к файлу / имя таблицы
Обсудите: Что лучше передать через XCom — 10 000 строк телеметрии букс или имя таблицы PostgreSQL с этими данными?

Классический push / pull

def push_loco_stats(**context):
    stats = {
        "vl80s_active":          12,
        "avg_delay_min":         7.4,
        "critical_temp_events":  3
    }
    # push: сохранить в XCom
    context["ti"].xcom_push(
        key="loco_stats",
        value=stats
    )

def pull_and_report(**context):
    # pull: прочитать из XCom
    stats = context["ti"].xcom_pull(
        task_ids="push_loco_stats",
        key="loco_stats"
    )
    print(f"ВЛ80С активных: {stats['vl80s_active']}")
    print(
        f"Среднее опоздание: "
        f"{stats['avg_delay_min']} мин"
    )
    print(
        f"Перегревов букс: "
        f"{stats['critical_temp_events']}"
    )
Покажите в Airflow UI вкладку XCom для конкретного Task Instance. Подчеркните ограничение по размеру — это частая ошибка у новичков.

TaskFlow API: @dag и @task

Зачем нужен TaskFlow?

  • Чище и короче классического подхода с операторами
  • XCom работает автоматически через return / аргументы
  • Зависимости задач определяются по вызовам функций
  • Поддерживается с Airflow 2.0+
Классический:
PythonOperator + xcom_push/pull + set_downstream()

TaskFlow:
Обычные Python-функции с декораторами

Структура TaskFlow DAG

from airflow.decorators import dag, task
from datetime import datetime

@dag(
    schedule="0 6,14,22 * * *",  # 3 смены в сутки
    start_date=datetime(2024, 1, 1),
    catchup=False,
    tags=["rzd", "tch-15"]
)
def loco_shift_report():

    @task
    def get_shift_data(ds=None):
        # ds — автоматически из контекста Airflow
        return {"date": ds, "depot": "TCH-15"}

    @task
    def calculate_kpi(shift_info: dict):
        # shift_info — XCom из предыдущей задачи
        return {"otd": 94.2, "fuel_norm": 98.1}

    @task
    def send_report(kpi: dict):
        print(f"OTD смены: {kpi['otd']}%")
        print(f"Норма топлива: {kpi['fuel_norm']}%")

    # Цепочка — через обычные вызовы функций
    info = get_shift_data()
    kpi  = calculate_kpi(info)
    send_report(kpi)

dag_instance = loco_shift_report()
Напишите на доске: «PythonOperator + xcom_push» vs «@task + return» — попросите сравнить количество строк. TaskFlow сокращает код в 2-3 раза.

XCom в TaskFlow: всё работает само

Классический XCom

def check_axle_temp(**context):
    events = [
        {"loco": "VL80S-1234", "temp_c": 87},
        {"loco": "2TE116-567", "temp_c": 74},
    ]
    context["ti"].xcom_push(
        key="hot_events",
        value=events
    )

def alert_dispatcher(**context):
    events = context["ti"].xcom_pull(
        task_ids="check_axle_temp",
        key="hot_events"
    )
    for e in events:
        if e["temp_c"] > 80:
            print(
                f"ПЕРЕГРЕВ БУКС: "
                f"{e['loco']} — {e['temp_c']}°C"
            )
# + ручное создание операторов и зависимостей

TaskFlow (автоматический XCom)

@task
def check_axle_temp(ds=None) -> list:
    # return -> автоматически xcom_push
    return [
        {"loco": "VL80S-1234", "temp_c": 87},
        {"loco": "2TE116-567", "temp_c": 74},
    ]

@task
def alert_dispatcher(events: list):
    # аргумент -> автоматически xcom_pull
    crit = Variable.get(
        "axle_temp_critical",
        default_var=80
    )
    for e in events:
        if e["temp_c"] > int(crit):
            print(
                f"ПЕРЕГРЕВ: {e['loco']} "
                f"{e['temp_c']}°C !!!"
            )

# В теле DAG — просто вызов:
evts = check_axle_temp()
alert_dispatcher(evts)

Результат: Меньше кода, нет ручного push/pull

Акцентируйте: TaskFlow не убирает XCom, он автоматизирует его. Данные всё равно хранятся в метаданных Airflow — ограничение по размеру сохраняется.

DAG анализа задержек смены — полный код

from airflow.decorators import dag, task
from airflow.models import Variable
from datetime import datetime

# Airflow Variables: depot_code=TCH-15, delay_threshold_min=15

@dag(
    schedule="0 */8 * * *",
    start_date=datetime(2024, 3, 1),
    catchup=False,
    tags=["rzd", "schedule-analysis"],
)
def shift_delay_analysis():

    @task
    def extract_delays(ds=None):
        depot     = Variable.get("depot_code",         default_var="TCH-15")
        threshold = int(Variable.get("delay_threshold_min", default_var=15))
        # SQL с шаблоном даты
        sql = f"""
            SELECT train_number, delay_min, route_from, route_to
            FROM rzd_analytics.schedule_adherence
            WHERE date = '{ds}'
              AND delay_min > {threshold}
        """
        return {"depot": depot, "date": ds, "sql": sql}

    @task
    def calculate_otd(data: dict):
        print(f"Calculating OTD for {data['depot']} on {data['date']}...")
        # XCom автоматически передаёт возврат @task
        return {"otd_pct": 94.2, "total_trains": 48, "delayed": 3}

    @task
    def create_report(kpi: dict, ds=None):
        print(f"OTD на {ds}: {kpi['otd_pct']}%")
        print(f"Рейсов: {kpi['total_trains']}, опоздавших: {kpi['delayed']}")

    data = extract_delays()
    kpi  = calculate_otd(data)
    create_report(kpi)

dag_instance = shift_delay_analysis()
Разберите код построчно. Обратите внимание на: 1) ds как аргумент функции — из контекста Airflow; 2) Variable.get с default_var — защита от отсутствующей переменной; 3) автоматический XCom через return / аргументы @task.

Лабораторная работа — обзор

Тема

DAG анализа расхода топлива по сменам с XCom и шаблонами дат — полная реализация на TaskFlow API

Что вы сделаете (8 шагов)

  1. Развернёте схему rzd_analytics в PostgreSQL
  2. Загрузите тестовые данные из CSV
  3. Напишете полный TaskFlow DAG
  4. Добавите обработку ошибок и алерты
  5. Настроите динамические пороги через Variables
  6. Запустите DAG за несколько исторических дат
  7. Проанализируете результаты в Airflow UI
  8. Выполните задания повышенной сложности

Ожидаемые результаты

  • Работающий DAG с полной параметризацией
  • Отчёт об отклонениях от норм расхода топлива
  • Алерты при превышении температуры букс 80°C
  • Метрики OTD за анализируемый период

Итоги модуля 04

Ключевые понятия

  • Jinja2 — динамические значения в параметрах задач
  • ds / prev_ds / next_ds — макросы дат для инкрементальной загрузки
  • Variables — конфигурация без изменения кода и деплоя
  • dag_run.conf — параметры при ручном запуске
  • XCom — передача малых значений между задачами
  • @dag / @task — чистый Python без шаблонного кода
