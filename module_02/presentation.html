Анатомия DAG-файла Python

Типичный DAG-файл состоит из пяти блоков:

  1. Импорты — Airflow, операторы, stdlib
  2. Константы — пути, параметры
  3. default_args — умолчания задач
  4. Python-функции — логика задач
  5. Объявление DAG — задачи + зависимости

Файл хранится в директории dags/.
Планировщик сканирует её каждые 30 секунд. 


# 1. Импорты
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime, timedelta

# 2. Константы
CSV_PATH = "/opt/airflow/data/buxa.csv"

# 3. default_args
default_args = {
    "owner": "rzd-tche15",
    "retries": 2,
}

# 4. Функции задач
def read_data(**context):
    import pandas as pd
    df = pd.read_csv(CSV_PATH)
    return len(df)

# 5. Объявление DAG
with DAG("buxa_monitor", ...):
    t1 = PythonOperator(
        task_id="read_data",
        python_callable=read_data,
    )
Покажите студентам, что каждый из пяти блоков имеет чёткую ответственность. Смешивать их не рекомендуется — это усложняет тестирование.

Синтаксис: with DAG vs @dag

Классический: with DAG


from airflow import DAG
from datetime import datetime

with DAG(
    dag_id="buxa_monitor_v1",
    schedule="0 * * * *",
    start_date=datetime(2024, 3, 1),
    catchup=False,
    tags=["rzd", "safety"],
) as dag:

    # задачи объявляются здесь
    ...

Явный Удобен при работе с несколькими DAG в одном файле.

Декоратор: @dag


from airflow.decorators import dag, task
from datetime import datetime

@dag(
    schedule="0 * * * *",
    start_date=datetime(2024, 3, 1),
    catchup=False,
    tags=["rzd", "safety"],
)
def buxa_monitor_v2():
    """Мониторинг температуры букс ТЧЭ-15."""

    @task
    def read_telemetry():
        import pandas as pd
        return pd.read_csv("/data/buxa.csv")

    read_telemetry()

buxa_monitor_v2()

Современный TaskFlow API — меньше кода, нативные XCom через return.

Рекомендация: в этом курсе используем with DAG — легче читать при обучении. В production оба варианта валидны.

TaskFlow API (декоратор) появился в Airflow 2.0. Он удобнее для новых DAG, но with DAG более прозрачен при обучении.

default_args — умолчания для всех задач DAG


default_args = {
    # Кто отвечает за DAG
    "owner": "rzd-analytics",

    # Повторы при падении задачи
    "retries": 3,
    "retry_delay": timedelta(minutes=10),

    # Email-уведомления
    "email_on_failure": True,
    "email": ["duty_engineer@rzd.ru"],
    "email_on_retry": False,

    # Таймаут выполнения задачи
    "execution_timeout": timedelta(minutes=30),

    # Не ждать успеха предыдущего Run
    "depends_on_past": False,
}

Как работает наследование

default_args — базовые значения для всех задач DAG.

Задача может переопределить любой параметр: 

# Задача не нуждается в повторах
BashOperator(
    task_id="log_summary",
    bash_command="echo done",
    retries=0,  # переопределяем
)
Важно Параметры DAG (schedule, catchup) — не из default_args. default_args — только для задач.
Частая ошибка студентов — пытаться положить schedule или start_date в default_args. Эти параметры передаются напрямую в DAG().

Операторы: BashOperator / PythonOperator / EmptyOperator

BashOperator

Выполняет bash-команду. Поддерживает Jinja-шаблоны.


BashOperator(
  task_id="check_csv",
  bash_command=(
    "wc -l /data/"
    "sensor_readings.csv"
    " && echo 'OK {{ ds }}'"
  ),
)

Использование в РЖД: проверка файлов, запуск скриптов выгрузки, архивирование логов.

PythonOperator

Вызывает Python-функцию. Передаёт context через **kwargs.


PythonOperator(
  task_id="validate_temp",
  python_callable=check_buxa,
  op_kwargs={
    "threshold": 80,
  },
)

Использование в РЖД: валидация телеметрии, расчёт KPI, обращение к PostgreSQL.

EmptyOperator

Ничего не делает. Используется как точка входа/выхода или развилка.


from airflow.operators.empty \
  import EmptyOperator

pipeline_start = EmptyOperator(
  task_id="pipeline_start",
)
pipeline_end = EmptyOperator(
  task_id="pipeline_end",
)

Структурирует граф DAG, упрощает визуализацию в UI.

Жизненный цикл в ТЧЭ-15

Сценарий: перегрев буксы локомотива ВЛ80С-1024

read_telemetry: success
↓
validate_temp: failed (80°C превышен)
↓ (ожидает)
insert_db: upstream_failed
↓ (не запустилась)

Задача с trigger_rule="all_done" запустится всегда — независимо от статуса upstream-задач.

Покажите в реальном UI как выглядят статусы. upstream_failed — один из самых важных для понимания каскадного эффекта.

DAG Run vs Task Instance

DAG Run

  • Конкретный запуск всего DAG
  • Имеет run_id: scheduled__2024-03-01T00:00:00
  • Имеет execution_date (logical date)
  • Состояние: running / success / failed
  • Создаётся по расписанию или вручную

Task Instance

  • Конкретный запуск одной задачи в рамках DAG Run
  • Идентифицируется: dag_id + task_id + run_id
  • Хранит: лог, время запуска, XCom, статус
  • Можно перезапустить в изоляции (Clear)

Аналогия для ТЧЭ-15

Понятие AirflowАналог в депо
DAGТехнологическая карта ТО-2
DAG RunКонкретное ТО-2 локомотива 15 марта
TaskПункт карты: "проверить буксы"
Task InstanceВыполнение пункта слесарем Ивановым 15 марта
ЛогЗапись в журнале с подписью

Ключевой момент: Grid View в UI — это сетка Task Instance × DAG Run. Каждая ячейка — отдельный Task Instance со своим логом.

Аналогия с ТО-2 обычно хорошо заходит для аудитории РЖД. Попросите студентов придумать свою аналогию.

Graph View и Grid View в Airflow UI

Graph View

  • Показывает топологию одного DAG Run
  • Каждый узел = задача, цвет = статус
  • Стрелки = зависимости
  • Клик по задаче → лог, детали, Clear/Mark
  • Полезно при диагностике конкретного запуска

Grid View

  • Столбцы = DAG Run (время ↑)
  • Строки = задачи DAG
  • Ячейка = Task Instance
  • Показывает историю всех запусков
  • Полезно для анализа тренда: какая задача часто падает?

Действия над Task Instance

ДействиеКогда применять
ClearПерезапустить задачу и все downstream
Mark SuccessПринудительно пометить успешной (обход ошибки)
Mark FailedПринудительно остановить задачу
LogПросмотр stdout/stderr задачи
XComЗначения, переданные между задачами

DAG: buxa_temp_monitor — полный код


from airflow import DAG
from airflow.operators.python import PythonOperator
from airflow.operators.bash import BashOperator
from datetime import datetime, timedelta
import pandas as pd
import logging

default_args = {
    "owner": "rzd-analytics",
    "retries": 3,
    "retry_delay": timedelta(minutes=10),
    "email_on_failure": True,
    "email": ["duty_engineer@rzd.ru"],
}

with DAG(
    "buxa_temp_monitor",
    schedule="0 * * * *",
    start_date=datetime(2024, 3, 1),
    catchup=False,
    default_args=default_args,
    tags=["rzd", "safety"],
) as dag:

    def check_buxa_temperature(**context):
        df = pd.read_csv("/data/sensor_readings.csv")
        critical = df[
            (df["sensor_type"] == "buxa_temp_c") &
            (df["value"] > 80)
        ]
        if len(critical) > 0:
            logging.warning(f"CRITICAL: {len(critical)} buxa overheating!")
        return len(critical)

    t1 = PythonOperator(
        task_id="read_telemetry",
        python_callable=lambda: pd.read_csv("/data/sensor_readings.csv"),
    )
    t2 = PythonOperator(
        task_id="check_buxa_temp",
        python_callable=check_buxa_temperature,
    )
    t3 = BashOperator(
        task_id="log_summary",
        bash_command="echo 'Buxa check complete at {{ ds }}'",
    )
    t1 >> t2 >> t3
Разберите каждую часть кода. Обратите внимание на default_args, email-уведомление и Jinja-шаблон {{ ds }} в BashOperator.
