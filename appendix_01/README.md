# Приложение 1. Лабораторная работа: проектирование DAG без внешних источников данных

**Курс:** Введение в Apache Airflow
**Охват модулей:** 1–6 (Введение, Устройство DAG, Календарное планирование, Шаблоны заданий, Зависимости, Потоки обработки)
**Организация:** РЖД, Западно-Сибирская дирекция тяги, депо Новосибирск-Главный (ТЧЭ-15)
**Платформа:** Yandex Managed Service for Apache Airflow™
**Продолжительность:** 90–120 минут
**Уровень:** Закрепляющий (после модуля 6)

---

## Чем это приложение отличается от лабораторных модулей 1–6

Лабораторные работы модулей 1–6 завязаны на **внешние источники данных** —
CSV в Yandex Object Storage, таблицы Managed PostgreSQL, сенсоры файлов.
Это правильно для production, но смешивает два навыка: *работу с источниками*
и *проектирование самого DAG*.

Это приложение **намеренно убирает все внешние источники**. Ни одного обращения
к S3, PostgreSQL, HTTP или локальной файловой системе. Телеметрия локомотивов
**генерируется внутри DAG** детерминированно из даты запуска. Благодаря этому:

- не нужны бакеты, Connections к данным, загрузка CSV — порог входа минимальный;
- любой `backfill` полностью **воспроизводим** (один `execution_date` → один результат);
- всё внимание — на «скелете» DAG: **расписании, переменных, шаблонах, зависимостях
  и проектировании потоков обработки**.

> Единственное «внешнее» взаимодействие — это деплой `.py`-файла в бакет DAG-ов,
> привязанный к кластеру Managed Airflow. Это механизм доставки кода, а не источник данных.

## Сквозной сценарий

Депо ТЧЭ-15 раз в сутки прогоняет служебный конвейер мониторинга парка:
снимает суточную телеметрию локомотивов (электровозы ВЛ80/ЭП2К, тепловозы
2ТЭ116/ЧМЭ3, электропоезд ЭД4М), параллельно анализирует три метрики
(**расход топлива**, **перегрев букс**, **OTD по расписанию**), собирает сводку
и при отклонениях формирует сигнал диспетчеру.

```
start
  → print_run_context        (демонстрация шаблонов Jinja)
  → generate_telemetry       (синтез данных, без внешних источников)
  → analyze (TaskGroup, fan-out):
        ├── fuel              (удельный расход, норма из Variable)
        ├── axlebox_temp      (перегрев букс, лимит из Variable)
        └── schedule          (OTD, порог из Variable)
  → build_report             (fan-in: сводка по трём метрикам)
  → route_by_alert           (ветвление @task.branch)
        ├── raise_alert       (есть отклонения)
        └── no_alert          (всё в норме)
  → finalize                 (trigger_rule = none_failed_min_one_success)
  → end
```

### Шаг 7. Разберите основной DAG: шаблоны, зависимости, потоки

Откройте `appendix1_depot_pipeline.py` и пройдите по блокам.

**7.1. Шаблоны заданий (Модуль 4).** Задача `print_run_context` (BashOperator)
не содержит ни одного «живого» значения — всё подставляет Jinja:

```python
'echo "Депо       : {{ var.value.depot_code }}"; '
'echo "Дата (ds)  : {{ ds }}"; '
'echo "Смена      : {{ shift_by_hour(ts) }}"; '          # пользовательский макрос
'echo "Парк (var) : {{ var.json.appendix1_fleet.electric | join(\', \') }}"; '
'echo "Вчера      : {{ macros.ds_add(ds, -1) }}"'        # встроенный макрос
```

Здесь задействованы: переменные в шаблоне (`var.value`, `var.json`),
встроенные макросы (`ds`, `ts`, `macros.ds_add`), фильтр Jinja (`join`),
`params` и **пользовательский макрос** `shift_by_hour`, объявленный в DAG через
`user_defined_macros`.

**7.2. Fan-out — параллельный анализ (Модуль 6).** TaskGroup `analyze`
содержит три независимые задачи (`fuel`, `axlebox_temp`, `schedule`).
Они получают одни и те же данные и выполняются **параллельно**.

**7.3. Fan-in — сборка (Модуль 6).** Задача `build_report` зависит сразу
от всех трёх задач анализа и объединяет их результаты.

**7.4. Ветвление (Модуль 5).** `route_by_alert` помечена `@task.branch`
и возвращает `task_id` одной из веток — `raise_alert` или `no_alert`.

**7.5. Trigger rule (Модуль 5).** Задача `finalize` использует
`trigger_rule="none_failed_min_one_success"`, чтобы выполниться при любой
выбранной ветке (вторая ветка будет `skipped`).

**7.6. Проектирование связей (Модуль 5).** В конце файла:

```python
chain(start, print_context, telemetry)          # явная линейная цепочка
branch >> [raise_alert, no_alert] >> finalize >> end
```

Остальные связи (`telemetry → analyze → build_report → branch`) создаются
**автоматически** при передаче XCom между TaskFlow-задачами.

**Вопрос для обсуждения 6.** Почему связь `start → print_context → telemetry`
пришлось задавать через `chain()` вручную, а связь
`telemetry → analyze` появляется сама собой?

### Шаг 8. Запустите основной DAG и проверьте граф

1. Активируйте `appendix1_depot_pipeline` и нажмите **Trigger DAG**.
2. Откройте **Graph** и убедитесь, что структура соответствует схеме
   из раздела «Сквозной сценарий»: после `analyze` идёт «расхождение» на три
   задачи и «схождение» в `build_report`, затем ветвление и `finalize`.
3. Откройте задачу `print_run_context` → **Log** и сверьте подставленные
   значения шаблонов.
4. Откройте `build_report` → **XCom** и проверьте поля сводки:
   `otd_pct`, `avg_fuel_lkm`, `axlebox_hot`, `fuel_over_norm`.

### Шаг 9. Проверьте ветвление и trigger rule

1. В **Graph** найдите, какая ветка выполнилась (`raise_alert` / `no_alert`),
   а какая получила статус `skipped`.
2. Убедитесь, что `finalize` всё равно завершилась `success` —
   за это отвечает `trigger_rule="none_failed_min_one_success"`.

**Эксперимент.** Откройте Variables и временно поставьте `delay_threshold_min = 0`.
Перезапустите DAG (**Clear** или **Trigger**). OTD упадёт ниже целевых 85 %,
ветвление уйдёт в `raise_alert`. Верните значение `15` обратно.

### Шаг 10. Выполните backfill (Модуль 3)

Так как данные генерируются детерминированно, backfill безопасен и воспроизводим.
Поставьте DAG на паузу и запустите backfill за неделю:

```bash
airflow dags backfill \
    --dag-id appendix1_depot_pipeline \
    --start-date 2024-03-01 \
    --end-date   2024-03-07 \
    --reset-dagruns
```

Ожидаемый результат: 7 успешных run-ов (по одному в сутки). В **Grid** все
ячейки зелёные. Повторный backfill за ту же дату даёт **тот же** XCom-результат
`build_report` — убедитесь в этом, сравнив значения до и после.
