01

Введение в Airflow

Что это и зачем
  • Airflow — это оркестратор: запускает задачи в нужном порядке, следит за сбоями и перезапусками. Заменяет хаос из cron-скриптов.
  • Пайплайн описывается кодом на Python (DAG), а не настройками в UI — это версионируется и тестируется.
  • Четыре кита архитектуры: Scheduler (планирует), Executor/Workers (выполняют), Webserver (UI), MetaDB (состояние).
Запомнить: Airflow управляет потоком задач, но сам данные «руками» не обрабатывает — он их дирижирует.
Главный сдвиг мышления: «расписание как код». Airflow не ETL-инструмент, а планировщик-дирижёр.
02

Устройство DAG

Из чего состоит пайплайн
  • DAG — направленный граф без циклов: вершины это задачи (Task), рёбра — порядок их выполнения.
  • Operator — шаблон задачи (Bash, Python, Empty…); Task — его конкретный экземпляр в DAG.
  • Различайте DAG Run (один запуск всего графа за дату) и Task Instance (одна задача в этом запуске) — на этом строится весь UI.
  • Состояния задачи (success, failed, up_for_retry…) видны в Grid/Graph View — это главный инструмент диагностики.
Запомнить: один DAG-файл = один пайплайн; одна задача должна делать одну понятную вещь.
Терминология DAG / Task / Operator / DAG Run / Task Instance — фундамент, на который опираются все следующие модули.
03

Календарное планирование

Когда срабатывает DAG
  • Расписание задаётся через schedule (cron или пресет @daily) и точку отсчёта start_date.
  • DAG запускается в конце интервала, а не в его начале — частый источник путаницы с датами.
  • catchup=True заставляет Airflow «догнать» все пропущенные интервалы; backfill — пересчитать историю вручную.
  • Время — всегда в явной таймзоне (pendulum); max_active_runs ограничивает число параллельных запусков.
Запомнить: дата запуска (data_interval) — это период, за который считаются данные, а не «сейчас».
Ключевая ловушка новичков: DAG за 1 июня фактически стартует в начале 2 июня. catchup может неожиданно запустить сотни прогонов.
04

Шаблоны заданий

Гибкость без правки кода
  • Jinja2 подставляет в задачи макросы ({{ ds }} — дата интервала) — основа инкрементальной обработки «только новые данные».
  • Variables хранят конфигурацию отдельно от кода; dag_run.conf передаёт параметры при ручном запуске.
  • XCom — механизм передачи небольших значений между задачами (не для больших данных!).
  • TaskFlow API (@dag/@task) делает XCom и зависимости автоматическими — код выглядит как обычные функции.
Запомнить: через XCom гоняем ссылки и метаданные, сами данные — в Object Storage / БД.
Переход от захардкоженных дат к {{ ds }} — момент, когда DAG становится переиспользуемым.
05

Зависимости задач

Порядок и ожидание
  • Порядок задаётся оператором >> (a >> b = «b после a»); из этого Airflow строит граф.
  • Типовые формы: линейная цепочка, fan-out (один → многие), fan-in (многие → один), diamond.
  • Сенсоры ждут наступления события (появился файл, прошло время, готова строка в БД) перед стартом следующих задач.
  • Режим reschedule освобождает воркер на время ожидания — на длинных ожиданиях экономит ресурсы против poke.
Запомнить: в Managed Airflow нет ФС — вместо FileSensor используем S3KeySensor (Yandex Object Storage).
Сенсоры — способ «дождаться» внешних данных. Важно про reschedule vs poke: poke держит слот воркера занятым.
06

Потоки обработки

Ветвление и динамика
  • BranchPythonOperator выбирает, какую ветку графа выполнять, по условию в данных.
  • ShortCircuitOperator останавливает пайплайн ниже по течению, если условие не выполнено.
  • TaskGroup визуально и логически группирует задачи — граф остаётся читаемым при росте.
  • Dynamic Task Mapping (.expand()) разворачивает одну задачу в N параллельных по числу элементов на входе — число известно только в рантайме.
Запомнить: ветвление управляет тем, что выполнять; mapping — тем, сколько раз параллельно.
Dynamic Task Mapping — мощный приём: например, по одной задаче на каждую серию локомотивов, не зная их число заранее.
07

Пользовательские компоненты

Расширяем Airflow
  • Когда готового провайдера нет (ведомственные системы РЖД) — пишут свой оператор, наследуя BaseOperator и реализуя execute().
  • Hook инкапсулирует подключение к внешней системе и берёт логин/пароль из Connections — переиспользуется в разных операторах.
  • Кастомный сенсор — это метод poke(), возвращающий True, когда данные готовы.
  • Plugins регистрируют все эти компоненты, чтобы их видел весь Airflow.
Запомнить: оператор = «что сделать», хук = «как подключиться». Не дублируйте — выносите доступ в хук.
Главное разделение ответственности: бизнес-логика в операторе, доступ к системе — в хуке через Connection.
08

Тестирование

Качество до прода
  • DAG — это код, и его надо тестировать: минимум — проверка, что DagBag загружается без ошибок импорта.
  • pytest + unittest.mock позволяют проверять логику задач, не дёргая реальные БД и API.
  • airflow tasks test прогоняет одну задачу за дату локально, без записи в метабазу.
  • Тесты встраиваются в CI/CD (GitHub Actions) — битый DAG не доедет до production-бакета.
Запомнить: ошибка импорта в DAG ломает Scheduler — тест на загрузку DagBag обязателен.
Мокирование внешних систем — ключ к быстрым и надёжным тестам. Тест на парсинг DAG ловит большинство опечаток.
09

Задачи в контейнерах

Docker, Kubernetes, ML
  • Контейнер изолирует зависимости задачи от Airflow — у ML-задачи свои версии библиотек, не конфликтующие с окружением.
  • DockerOperator / KubernetesPodOperator запускают готовый образ; данные передаются через volumes и переменные окружения.
  • Образы хранятся в Yandex Container Registry; для задач задаются лимиты CPU/памяти.
  • Airflow только оркестрирует контейнер — тяжёлые вычисления идут внутри пода, не на воркере.
Запомнить: контейнеры — способ запускать «чужой» или ресурсоёмкий код (ML-прогноз перегрева букс) безопасно.
Пример модуля: ML-модель в контейнере предсказывает критическую температуру букс >80°C за 2 часа до события.
10

Практика использования

Что отличает прод-DAG
  • Идемпотентность: повторный запуск задачи даёт тот же результат и не дублирует данные (перезаписывайте партицию, а не добавляйте).
  • Атомарность: одна задача — одна ответственность; упала — понятно, где и что перезапускать.
  • Надёжность задаётся retries, callbacks и SLA; доступы — только через Connections, без паролей в коде.
  • Топ-антипаттернов: тяжёлый код на верхнем уровне DAG, большие данные в XCom, неидемпотентные вставки.
Запомнить: хороший DAG можно перезапустить за любую дату в любой момент — и ничего не сломается.
Идемпотентность — главный критерий зрелости пайплайна. Это то, что отличает учебный DAG от production.
11

Эксплуатация

Airflow под нагрузкой
  • Тип Executor определяет масштаб: Local (одна машина) → Celery/Kubernetes (много воркеров).
  • Pools и приоритеты не дают «прожорливым» задачам забить все слоты воркеров.
  • Метрики уходят в Prometheus (StatsD), визуализация — в Grafana, проблемы — в алерты (email/Telegram).
  • Метабазу и логи надо регулярно чистить — иначе они растут и тормозят систему.
Запомнить: в проде важно не «как написать DAG», а «как поддержать сотни DAG стабильными».
Самый инженерный модуль: масштабирование воркеров, наблюдаемость, обслуживание метабазы.
12

Безопасность

Доступ и секреты
  • RBAC: каждому — своя роль (DataEngineer, DataAnalyst, DutyOperator) и доступ только к нужным DAG.
  • Пароли и токены — не в Connections и не в коде, а в Secrets Backend (Yandex Lockbox).
  • Fernet Key шифрует чувствительные данные в метабазе (at-rest); доступ к UI — только по HTTPS.
  • Аудит-лог фиксирует, кто и что запускал — критично для ведомственной ж/д-инфраструктуры.
Запомнить: аутентификация (кто ты) + RBAC (что тебе можно) + секреты (где пароли) — три опоры безопасности.
Безопасность для инфраструктуры РЖД — не опция: разграничение доступа, защита секретов, прослеживаемость действий.

Главное за весь курс

Пайплайн как код. DAG на Python — версионируется, тестируется, переиспользуется.
Идемпотентность. Любой запуск за любую дату безопасен и повторяем.
Разделение ролей. Оператор / хук / сенсор, бизнес-логика отдельно от доступа.
Production-зрелость. Тесты, мониторинг, безопасность — не «потом», а часть DAG.
