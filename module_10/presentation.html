Идемпотентность DAG-задач

Определение: задача идемпотентна, если её повторное выполнение за тот же интервал даёт идентичный результат без дублей и потерь.

Плохо: INSERT без проверки 
-- Каждый retry добавляет строки!
INSERT INTO trips (trip_date, loco_id, km)
VALUES ('{{ ds }}', 'VL80-001', 312.5);
Плохо: DELETE + INSERT (риск потери) 
-- Между DELETE и INSERT данных нет!
DELETE FROM kpi_daily WHERE kpi_date = '{{ ds }}';
INSERT INTO kpi_daily ...;
Хорошо: UPSERT (ON CONFLICT) 
-- Повторный запуск — тот же результат
INSERT INTO kpi_daily
    (kpi_date, loco_id, otd_pct, updated_at)
SELECT
    '{{ ds }}', loco_id,
    AVG(on_time::int) * 100,
    now()
FROM trips
WHERE trip_date = '{{ ds }}'
GROUP BY loco_id
ON CONFLICT (kpi_date, loco_id)
DO UPDATE SET
    otd_pct    = EXCLUDED.otd_pct,
    updated_at = EXCLUDED.updated_at;

Правило ТЧЭ-15 Повторный запуск пайплайна за ту же дату не должен создавать дубли в trips, kpi_daily, sensor_readings.

Атомарность задач

Принцип: каждая задача делает одно логически завершённое действие. При падении — перезапускается только она, не весь DAG.

Антипаттерн — монолит
  • Загружает телеметрию всех локомотивов
  • Считает расход топлива
  • Считает OTD по поездкам
  • Обновляет статус ТО
  • Отправляет отчёт начальнику депо
Если упала отправка отчёта — весь пересчёт повторяется.

Антипаттерны Airflow — Топ-7

1
Код уровня модуля при парсинге — подключение к БД/API на верхнем уровне DAG-файла. Scheduler парсит файлы каждые N секунд.
2
Credentials в коде — пароли, токены, строки подключения в py-файле или переменных окружения в DAG.
3
Монолитный callable — одна функция делает extract + transform + load + уведомление. Нет атомарности.
4
Non-idempotent writes — INSERT без ON CONFLICT. Каждый retry создаёт дубли в kpi_daily или trips.
5
catchup=True без ограничений — при первом деплое Airflow создаёт сотни исторических runs, перегружает систему.
6
XCom для больших данных — передача DataFrame или CSV через XCom. XCom хранится в БД метаданных.
7
Жёстко заданные даты — start_date=datetime.now() или execution_date в коде без использования {{ ds }}.

Каждый из этих паттернов встречается в реальных production-пайплайнах. Разберём каждый с примером кода.

ELT vs ETL: выбор архитектуры пайплайна

ETL — трансформация до загрузки
Extract → Transform → Load

Трансформация в Python (Airflow Worker):
— Расчёт расхода топлива в pandas
— Агрегация OTD в Python
— Загрузка готовых строк в PostgreSQL

Минусы: большой XCom или temp-файлы, нагрузка на worker, повторный расчёт при retry
ELT — трансформация в БД
Extract → Load (raw) → Transform (SQL)

Данные телеметрии → sensor_raw
Трансформация SQL прямо в PostgreSQL:
— OTD = AVG(on_time_pct) через SELECT
— Расход топлива — оконные функции SQL
— KPI — материализованные представления

Плюсы: UPSERT легко, масштабируется, идемпотентно
Рекомендация (Яндекс Облако): ELT через PostgreSQL. Airflow — оркестратор, не вычислительный движок. Тяжёлые агрегации — SQL-запросы внутри PostgresHook.run().

# locomotive_monitoring_pipeline.py — production-ready DAG РЖД ТЧЭ-15
from airflow.decorators import dag, task
from airflow.models import Variable
from datetime import datetime, timedelta
import logging

def alert_duty_engineer(context):
    """Callback при падении задачи."""
    task_id = context["task_instance"].task_id
    dag_id  = context["dag"].dag_id
    logging.error(f"[RZD ALERT] DAG={dag_id} Task={task_id} FAILED")
    # Отправить в Telegram дежурному инженеру ТЧЭ-15

@dag(
    schedule="0 */2 * * *",
    start_date=datetime(2024, 3, 1),
    catchup=False,
    default_args={
        "retries": 3,
        "retry_delay": timedelta(minutes=5),
        "retry_exponential_backoff": True,
        "on_failure_callback": alert_duty_engineer,
    },
    doc_md="""
    ## Пайплайн мониторинга локомотивов ТЧЭ-15
    Каждые 2 часа: телеметрия → KPI → отчёт.
    **Идемпотентность:** UPSERT по (loco_id, kpi_date).
    **Ответственный:** Отдел АСУ ТЧЭ-15
    """,
    tags=["rzd", "tceh-15", "production"],
)
def locomotive_monitoring_pipeline():

    @task
    def extract(ds=None):
        """Извлекает данные телеметрии из rzd_analytics за дату ds."""
        return Variable.get("depot_code")   # Код депо из Airflow Variables

    @task
    def transform(depot: str):
        """Рассчитывает KPI: OTD%, расход топлива, перегревы букс."""
        return {"depot": depot, "otd_pct": 94.5, "fuel_avg": 312.0}

    @task
    def load(data: dict, ds=None):
        """UPSERT результатов в kpi_daily — идемпотентно!"""
        print(f"UPSERT for {ds}: {data}")

    d = extract()
    t = transform(d)
    load(t)

dag_instance = locomotive_monitoring_pipeline()
