Сценарий модуля

ML-модель прогнозирования перегрева букс локомотивов запускается как Docker-контейнер. Предсказание: критическая температура > 80°C за 2 часа до события.

Зачем контейнеры в Airflow?

Проблемы без контейнеров

  • ML-модель требует TensorFlow 2.x, Airflow — Python 3.10 без TF
  • Конфликты зависимостей между задачами
  • Разные версии pandas/scikit-learn для разных DAG
  • Задача на R, Julia или C++ в Python-окружении
  • Невозможность воспроизвести среду при деплое

Решение: DockerOperator

Принцип изоляции

📦Каждая задача — отдельный контейнер
🔒Изолированное окружение с фиксированными версиями
🚀Воспроизводимые результаты на любом сервере
📊Масштабирование через Kubernetes

Принципы многослойного образа

  • Зависимости — отдельный слой для кэша

  • Секреты через env vars, не COPY
  • Минимальный базовый образ (-slim)

Передача данных: тома (volumes)

Схема монтирования томов

🖥️Host: /data/input/
↕️ bind mount
📦Container: /app/data/ (read-only)
🖥️Host: /data/predictions/
↕️ bind mount
📦Container: /app/output/ (read-write)
🖥️Host: /models/
↕️ bind mount
📦Container: /app/models/ (read-only)
from docker.types import Mount as DockerMount

predict_task = DockerOperator(
    task_id="predict_buxa_failures",
    image="registry.yandex.net/rzd-tceh15/"
          "buxa-predictor:v1.2",
    mounts=[
        # Входные данные датчиков (только чтение)
        DockerMount(
            source="/data/sensor_readings",
            target="/app/data",
            type="bind",
            read_only=True,
        ),
        # Результаты прогноза (запись)
        DockerMount(
            source="/data/predictions",
            target="/app/output",
            type="bind",
            read_only=False,
        ),
        # Файл модели (только чтение)
        DockerMount(
            source="/models/buxa",
            target="/app/models",
            type="bind",
            read_only=True,
        ),
    ],
    docker_url="unix:///var/run/docker.sock",
    auto_remove=True,
)

Скрипт predict_buxa_failure.py

#!/usr/bin/env python3
"""
Прогноз перегрева букс локомотивов ТЧЭ-15
Модель: Random Forest (scikit-learn)
Запускается как Docker-контейнер через DockerOperator
"""
import os
import pandas as pd
import joblib
from datetime import datetime

TARGET_DATE    = os.environ.get("TARGET_DATE", datetime.today().strftime("%Y-%m-%d"))
DEPOT_CODE     = os.environ.get("DEPOT_CODE", "TCH-15")
THRESHOLD_TEMP = float(os.environ.get("THRESHOLD_TEMP", 80))
DATA_DIR       = "/app/data"
OUTPUT_DIR     = "/app/output"
MODEL_PATH     = "/app/models/buxa_rf_model.joblib"

print(f"[INFO] Запуск прогноза: дата={TARGET_DATE}, депо={DEPOT_CODE}")

# Загрузка данных датчиков
df = pd.read_csv(f"{DATA_DIR}/sensor_readings_{TARGET_DATE.replace('-','')}.csv")
print(f"[INFO] Загружено {len(df)} записей датчиков")

# Признаки для модели
FEATURE_COLS = [
    "buxa_temp_celsius", "speed_kmh", "traction_current_a",
    "temp_delta_30min",  "engine_hours", "ambient_temp_celsius",
]
X = df[FEATURE_COLS].fillna(df[FEATURE_COLS].median())

# Загрузка модели и прогноз
model = joblib.load(MODEL_PATH)
df["failure_prob"] = model.predict_proba(X)[:, 1]
df["failure_flag"] = (df["failure_prob"] > 0.7).astype(int)

# Фильтрация критических случаев
critical = df[df["failure_flag"] == 1].copy()
print(f"[WARN] Критических прогнозов: {len(critical)}")

# Сохранение результатов
out_path = f"{OUTPUT_DIR}/predictions_{TARGET_DATE.replace('-','')}.csv"
critical[[
    "loco_number", "loco_series", "buxa_position",
    "failure_prob", "buxa_temp_celsius", "timestamp",
]].to_csv(out_path, index=False)
print(f"[INFO] Прогнозы сохранены: {out_path}")

# XCom: вывод JSON в stdout
import json
result = {"critical_count": len(critical), "output_file": out_path, "date": TARGET_DATE}
print(json.dumps(result))  # Airflow читает последнюю строку stdout как XCom

Вопрос для обсуждения

Сценарий: ML-модель прогнозирования отказов букс требует TensorFlow 2.x. Основной Airflow использует Python 3.10 без TF. В модель нужно передать данные о рейсе: дату, номер локомотива, серию, данные датчиков за последние 24 часа (CSV-файл ~50 MB).

Вопросы для обсуждения (10 мин):
  • Какие данные безопасно передавать через переменные окружения?
  • Что правильнее передать через volume-монтирование?
  • Как передать строку подключения к PostgreSQL без хранения пароля в коде?
  • Если контейнер упал — как получить информацию об ошибке?

Подсказка: правило разделения

  • Env vars: параметры (даты, коды, пороги, флаги) — небольшие строки
  • Volumes: данные (CSV, модели, конфиги) — файлы любого размера
  • Secrets Backend: пароли, токены, ключи — никогда в env vars напрямую

Кейс для анализа

Ситуация в ТЧЭ-15: Контейнер с ML-моделью прогноза букс потребляет до 8 GB RAM при загрузке данных за 24 часа по всем локомотивам. На сервере Yandex Cloud 16 GB RAM. Если два рейса DAG запустятся параллельно (локомотивы ВЛ80С и 2ТЭ116 обрабатываются одновременно), суммарное потребление превысит 16 GB — сервер упадёт, задачи прервутся на середине.

Вопросы для анализа (группы по 3 чел., 15 мин):
  • Как ограничить параллелизм на уровне DAG и на уровне DockerOperator?
  • Можно ли разбить обработку по сериям локомотивов и обработать последовательно?
  • Какой тип инстанса Yandex Cloud выбрать для продакшн-деплоя?
  • Как настроить mem_limit чтобы при OOM контейнер падал сам, а не убивал ОС?
Варианты решения: max_active_tasks=1 в DAG | mem_limit="7g" в DockerOperator | пул docker_pool с 1 слотом | разбивка на батчи по сериям локомотивов

Вопрос для обсуждения 2

Дилемма архитектора: Команда ТЧЭ-15 внедряет аналитическую платформу. Сейчас Airflow работает на одной VM Ubuntu 22.04 в Yandex Cloud (16 vCPU, 32 GB RAM). Планируется 15 ML-задач с контейнерами, суммарная нагрузка — до 80 GB RAM в пике.

DockerOperator vs KubernetesPodOperator — что выбрать для ТЧЭ-15?
  • DockerOperator: простота, быстрый старт, но один сервер
  • KubernetesPodOperator: сложнее настройка, зато масштабируется на кластер нод
  • Yandex Managed Service for Kubernetes: готовая инфраструктура, но стоимость

Обсудите критерии выбора: команда 3 DevOps-инженеров, бюджет ограничен, SLA 99.5%.

    description="ML-пайплайн прогноза перегрева букс локомотивов ТЧЭ-15",
    schedule="0 */4 * * *",
    start_date=datetime(2024, 3, 1),
    max_active_runs=1,
    default_args=default_args,
    tags=["rzd", "tceh15", "ml", "buxa"],
) as dag:

    # Шаг 1: Извлечение данных датчиков
    extract = PythonOperator(
        task_id="extract_sensor_data",
        python_callable=extract_sensor_readings,
        op_kwargs={"depot": "TCH-15", "date": "{{ ds }}"},
    )

    # Шаг 2: Предобработка в Docker-контейнере
    preprocess = DockerOperator(
        task_id="preprocess_sensor_data",
        image=f"{REGISTRY}/sensor-preprocessor:v2.0",
        command="python preprocess.py",
        environment={"TARGET_DATE": "{{ ds }}", "DEPOT": "TCH-15"},
        mounts=[DATA_MOUNT, OUT_MOUNT],
        mem_limit="3g", cpus=1.0,
        auto_remove=True,
    )

    # Шаг 3: ML-прогноз в Docker-контейнере
    predict = DockerOperator(
        task_id="predict_buxa_failures",
        image=f"{REGISTRY}/buxa-predictor:v1.2",
        command="python predict_buxa_failure.py",
        environment={
            "TARGET_DATE":    "{{ ds }}",
            "DEPOT_CODE":     "TCH-15",
            "THRESHOLD_TEMP": "80",
        },
        mounts=[OUT_MOUNT],
        mem_limit="6g", cpus=2.0,
        auto_remove=True,
        retrieve_output=True,
    )

    # Шаг 4: Запись прогнозов в PostgreSQL
    store = PostgresOperator(
        task_id="store_predictions",
        postgres_conn_id="pg_rzd_analytics",
        sql="sql/insert_buxa_predictions.sql",
    )

    extract >> preprocess >> predict >> store

Сравнение подходов: выбор оператора

Сценарий Рекомендуемый оператор Обоснование
Разработка и тестирование ML-модели DockerOperator Простота, быстрый старт, локальный Docker
Продакшн с одним сервером DockerOperator + resource limits Контроль ресурсов, ограничение параллелизма
Масштабируемый продакшн KubernetesPodOperator Автомасштабирование, изоляция namespace
Лёгкие Python-задачи PythonOperator Нет накладных расходов контейнера
ML на GPU (прогноз по видео) KubernetesPodOperator + GPU node GPU scheduling в K8s, resource limits для GPU
Managed Airflow в Яндекс Облаке KubernetesPodOperator Managed K8s + Yandex Container Registry
Рекомендация: начать с DockerOperator на VM, мигрировать на KubernetesPodOperator при росте нагрузки свыше 10 параллельных ML-задач.
