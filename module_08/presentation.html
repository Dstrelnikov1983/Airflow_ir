Зачем тестировать DAG?

Риски без тестирования
Пропущенное критическое событие — сбой в продакшне
Неверный расчёт метрик — ошибочные бизнес-решения
Некорректная обработка данных — порча витрин
Масштаб данных:
Десятки источников телеметрии
Сотни объектов → тысячи показаний/час

Что даёт тест-сьют

  • Уверенность при деплое новой версии DAG
  • Защита от регрессий бизнес-логики
  • Быстрая обратная связь (CI < 5 мин)
  • Документация через тесты
  • Безопасный рефакторинг

DagBag — тесты структуры DAG

Что такое DagBag?

Загрузчик DAG-файлов Airflow. Сканирует папку, импортирует Python-модули, собирает объекты DAG.

  • dagbag.dags — словарь dag_id → DAG
  • dagbag.import_errors — ошибки импорта
  • Работает без запущенного Airflow

Что проверяем структурно

  • Отсутствие ошибок импорта
  • Наличие нужных dag_id
  • Состав задач (task_ids)
  • Порядок зависимостей
  • Расписание и параметры
  • Теги, retries, catchup
from airflow.models import DagBag

def test_no_import_errors():
    bag = DagBag(dag_folder="dags/", include_examples=False)
    assert bag.import_errors == {}, f"Ошибки: {bag.import_errors}"

def test_dag_exists():
    bag = DagBag(dag_folder="dags/", include_examples=False)
    assert "buxa_temp_monitor" in bag.dags

pytest — фикстуры и параметризация

Фикстуры

  • @pytest.fixture — переиспользуемые объекты
  • scope="session" — дорогие ресурсы (DagBag)
  • scope="function" — изолированный mock
  • conftest.py — общие фикстуры

Параметризация

  • @pytest.mark.parametrize
  • Один тест × N наборов входных данных
  • Граничные значения пороговых показателей
  • normal / warning / critical
import pytest

@pytest.mark.parametrize("temp_c,expected", [

В тестах заменяем на Mock-объекты

Инструменты mock

  • @patch("module.Class") — патч импорта
  • MagicMock() — объект с любыми атрибутами
  • .return_value — задать возвращаемое значение
  • .side_effect — последовательность ответов
  • .assert_called_once() — проверить вызов
from unittest.mock import patch, MagicMock

@patch("dags.buxa_monitor.psycopg2.connect")
def test_db_connection_called(mock_connect):
    mock_conn = MagicMock()
    mock_connect.return_value.__enter__ = lambda s: mock_conn
    mock_connect.return_value.__exit__  = MagicMock(return_value=False)

    from dags.buxa_monitor import load_buxa_alerts
    load_buxa_alerts(alerts=[{"loco_id": "ВЛ80С-731", "temp_c": 87}])

    mock_conn.cursor().execute.assert_called_once()

Тестирование @task-функций

TaskFlow API (@task)

  • Функция обёрнута декоратором @task
  • При прямом вызове ведёт себя как обычная функция
  • Можно тестировать без Airflow runtime
  • XCom-обмен — через return/аргументы

Два способа тестирования

1. Прямой вызов функции — для unit-тестов бизнес-логики

2. .test() метод — для тестирования с Airflow context

from airflow.decorators import task

# --- DAG-файл (dags/buxa_monitor.py) ---
@task
def classify_readings(readings: list) -> dict:
    """Классифицировать показания датчиков букс."""
    alerts = [r for r in readings if r["temp_c"] >= 80]
    return {
        "total":    len(readings),
        "alerts":   len(alerts),
        "critical": [r for r in alerts if r["temp_c"] >= 90],
    }

# --- tests/test_buxa_task.py ---
def test_classify_readings_direct():
    """Прямой вызов @task функции — без Airflow."""
    from dags.buxa_monitor import classify_readings
    readings = [
        {"loco_id": "ВЛ80С-731", "buxa": "Л1", "temp_c": 65},
        {"loco_id": "2ТЭ116-927", "buxa": "П3", "temp_c": 82},
        {"loco_id": "ЭП2К-100",   "buxa": "Л4", "temp_c": 94},
    ]
    result = classify_readings.function(readings)  # .function — сырая функция
    assert result["total"]   == 3
    assert result["alerts"]  == 2
    assert len(result["critical"]) == 1

XCom тесты — проверка передачи данных

Что проверяем в XCom

  • xcom_push вызван с правильным ключом
  • xcom_pull получает корректные данные
  • Обработка None (отсутствующий XCom)
  • Тип и структура передаваемых данных

Мок TaskInstance (ti)

  • MagicMock() для объекта ti
  • ti.xcom_pull.return_value
  • ti.xcom_push.assert_called_with()
  • Проверка ключей: "readings", "alerts"
from unittest.mock import MagicMock

def test_xcom_push_alerts_key():
    """Таск должен записать 'buxa_alerts' в XCom."""
    mock_ti = MagicMock()
    sample_readings = [
        {"loco_id": "ВЛ80С-731", "buxa": "Л1", "temp_c": 87},
        {"loco_id": "2ТЭ116-927", "buxa": "П2", "temp_c": 60},
    ]
    mock_ti.xcom_pull.return_value = sample_readings

    from dags.buxa_monitor import process_readings
    process_readings(ti=mock_ti)

    # Проверяем, что push был вызван с нужным ключом
    push_kwargs = {
        call.kwargs["key"]
        for call in mock_ti.xcom_push.call_args_list
    }
    assert "buxa_alerts" in push_kwargs

def test_xcom_none_raises_value_error():
    """Если XCom вернул None — должна быть ValueError."""
    mock_ti = MagicMock()
    mock_ti.xcom_pull.return_value = None

    from dags.buxa_monitor import process_readings
    import pytest
    with pytest.raises(ValueError, match="buxa_readings XCom not found"):
        process_readings(ti=mock_ti)

airflow tasks test — ручная проверка

Команда airflow tasks test

  • Запускает один таск локально
  • Не записывает результат в БД Airflow
  • Не отмечает DagRun как выполненный
  • Удобна для отладки на VM Яндекс Облако

Синтаксис

airflow tasks test \
  <dag_id> \
  <task_id> \
  <execution_date>

# Пример для ТЧЭ-15:
airflow tasks test \
  buxa_temp_monitor \
  read_telemetry \
  2024-06-01

# Проверить рендер шаблонов
airflow tasks render \
  buxa_temp_monitor \
  log_summary \
  2024-06-01
Отличие от pytest: airflow tasks test использует реальное окружение Airflow (connections, variables), но без записи в метабазу. Используйте его для интеграционной проверки перед деплоем в Managed Airflow.

Вопрос для обсуждения

Ситуация:
Тесты DAG буксового контроля написаны с mock PostgreSQL. Тесты проходят, но в продакшне вставка падает из-за конфликта типов данных — temp_c передаётся как строка, а PostgreSQL ожидает FLOAT.

Вопрос: Как этого избежать? Какие дополнительные проверки добавить в тест, чтобы поймать ошибку типов данных до деплоя?
Подсказки для обсуждения:
  • Типизация аргументов функций (temp_c: float)
  • Проверка типов в assert (isinstance(val, float))
  • Интеграционный тест с SQLite вместо mock
  • Schema-валидация входных данных (pydantic)

Кейс для анализа

Инцидент в ТЧЭ-15:

После деплоя обновлённого DAG buxa_temp_monitor в пятницу вечером перестал работать расчёт OTD (on-time delivery) — все значения стали 0%. Тесты в CI проходили зелёными.

Расследование:
  • DAG изменили расписание с */4 * * * * на 0 */4 * * *
  • Тест расписания проверял только факт наличия строки, но не её значение
  • OTD-витрина обновлялась каждый час и не получала данных
  • Инцидент обнаружили только в понедельник утром

Вопрос: Как написать тест, который поймал бы эту ошибку? Какие атрибуты DAG нужно проверять?

import pytest
from dags.buxa_monitor import classify_temperature

# Пороги ТЧЭ-15:
#   < 80°C  — normal    (штатный режим)
#   80–89°C — warning   (предупреждение ТЧМИ)
#   >= 90°C — critical  (экстренная остановка)

@pytest.mark.parametrize("temp_c, expected_status", [
    # Нормальный диапазон
    (20,  "normal"),    # буксы в холодный день
    (55,  "normal"),    # типичный рабочий режим
    (79,  "normal"),    # граница нормы (не включительно 80)
    # Предупреждение
    (80,  "warning"),   # ровно порог предупреждения
    (85,  "warning"),   # середина диапазона warning
    (89,  "warning"),   # граница warning (не включительно 90)
    # Критический перегрев
    (90,  "critical"),  # ровно порог критического состояния
    (95,  "critical"),  # типичный перегрев при неисправности
    (120, "critical"),  # экстремальный перегрев
])
def test_classify_temperature_buxa(temp_c, expected_status):
    result = classify_temperature(temp_c)
    assert result == expected_status, (
        f"temp_c={temp_c}°C: ожидали '{expected_status}', "
        f"получили '{result}'"
    )

Итоги модуля 08

DagBag и структура

import_errors, task_ids, зависимости, расписание, catchup — всё это можно проверить без запуска Airflow.

pytest и параметризация

Фикстуры scope="session" для DagBag. @pytest.mark.parametrize для граничных значений показателей.

unittest.mock

@patch для PostgreSQL и REST API. MagicMock для TaskInstance. side_effect для последовательных ответов.

XCom тесты

Проверяем xcom_push с нужными ключами. Тестируем ValueError при None. Контролируем структуру передаваемых данных.

CI/CD GitHub Actions

4 job-а: Lint → Unit Tests → Coverage → Notify. Триггер на изменения в dags/** и tests/**.

airflow tasks test

Запуск одного таска локально без записи в метабазу. Удобно для интеграционной проверки перед деплоем в Яндекс Облако.
