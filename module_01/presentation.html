Apache Airflow — оркестратор рабочих процессов

Определение

Airflow — платформа с открытым исходным кодом для программного создания, планирования и мониторинга рабочих процессов обработки данных.

  • Разработан в Airbnb (2014), передан в Apache (2016)
  • Версия 2.x: полностью переработана архитектура
  • Язык: Python
  • Активное сообщество: 30 000+ GitHub ⭐

Ключевые принципы

Workflows as Code
Пайплайны описываются кодом Python — версионирование в Git, тестирование, повторное использование
Не для потоков реального времени
Airflow — планировщик батч-задач. Для RT используют Kafka/Flink. Идеален для ETL каждые 15 мин.
Применение:
Телеметрия → DWH → витрины BI → алерты по событиям
Подчеркните отличие от Kafka/Spark Streaming. Airflow — это планировщик, а не движок реального времени. Пример: собираем телеметрию каждые 15 минут и строим агрегаты за смену.

Архитектура Apache Airflow

Scheduler
Читает DAG-файлы, следит за расписанием, ставит задачи в очередь. Сердце системы.

Python process
Webserver
Flask-приложение. Предоставляет UI для мониторинга DAG, логов, ручного запуска.

Flask + Gunicorn
Executor
Решает, как выполнять задачи: локально, в очереди Celery, в Kubernetes.

LocalExecutor CeleryExecutor
MetaDB (PostgreSQL)
Хранит состояние всех DAG и задач, историю запусков, соединения, переменные. Критически важен.
Worker
Процессы, непосредственно выполняющие код задач. При CeleryExecutor — отдельные VM.
Нарисуйте схему на доске: Scheduler читает DAG → кладет TaskInstance в MetaDB → Executor забирает → Worker выполняет → результат в MetaDB → Webserver показывает статус.

Основные концепции: DAG, Task, Operator

DAG
Directed Acyclic Graph — граф задач без циклов. Описывает полный пайплайн обработки данных.
Пример:
telemetry_ingest_dag
запускается каждые 15 мин, обрабатывает телеметрию со всех устройств
Task
Единица работы внутри DAG. Каждая задача имеет статус: queued → running → success / failed.
Пример:
validate_sensor_value
проверяет: значение датчика в допустимых пределах. Если нет — алерт дежурному
Operator
Шаблон задачи. Определяет, что именно делать. Python, SQL, Bash, HTTP — всё это операторы.
Пример:
PostgresOperator
записывает агрегаты по расходу ресурсов в схему analytics

Зависимость задач: extract >> validate >> transform >> load >> notify

Объясните на примере: пайплайн телеметрии локомотива — это DAG. Шаги «читать CSV», «проверить температуру букс», «записать в PostgreSQL» — это Tasks. PythonOperator, PostgresOperator — это Operators.

Вариант Б: VM Ubuntu 22.04 (учебная)

# 1. Обновление системы
sudo apt update && sudo apt upgrade -y

# 2. Python 3.10 + pip
sudo apt install -y python3.10 python3-pip

# 3. Переменные окружения
export AIRFLOW_HOME=~/airflow
export AIRFLOW__CORE__EXECUTOR=LocalExecutor

# 4. Установка Airflow 2.8.x
CONSTRAINT_URL="https://raw.githubusercontent.com/apache/\
airflow/constraints-2.8.4/\
constraints-3.10.txt"
pip install "apache-airflow==2.8.4" \
  --constraint "${CONSTRAINT_URL}"

# 5. Инициализация БД
airflow db init

# 6. Создание администратора
airflow users create \
  --username admin --firstname RZD \
  --lastname Admin --role Admin \
  --email admin@tche15.rzd.ru
На учебной VM используем LocalExecutor — проще всего. В продуктиве нужен CeleryExecutor или Kubernetes. Managed Airflow в Яндекс Cloud — самый быстрый старт для команды.

Первый DAG: приём телеметрии локомотивов

from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime, timedelta

default_args = {
    "owner": "rzd-de-team",
    "retries": 2,
    "retry_delay": timedelta(minutes=5),
    "email_on_failure": True,
    "email": ["duty@tche15.rzd.ru"],
}

with DAG(
    dag_id="locomotive_telemetry_ingest",
    description="Ingestion of locomotive GLONASS telemetry for TChe-15",
    schedule="*/15 * * * *",          # каждые 15 минут
    start_date=datetime(2024, 3, 1),
    catchup=False,
    default_args=default_args,
    tags=["rzd", "telemetry", "ingest", "tche15"],
) as dag:

    def read_telemetry(**context):
        """Читает данные ГЛОНАСС для всех локомотивов депо."""
        print("Reading telemetry from GLONASS system...")
        # Здесь будет HTTP-запрос к API навигационной системы

    def validate_buxa_temp(**context):
        """Проверяет температуру букс. Критично: > 80°C."""
        print("Validating buxa temperatures...")
        # При превышении 80°C — генерация алерта

    ingest = PythonOperator(
        task_id="ingest_telemetry",
        python_callable=read_telemetry,
    )

    validate = PythonOperator(
        task_id="validate_buxa_temp",
        python_callable=validate_buxa_temp,
    )

    ingest >> validate   # validate запускается после ingest
Разберите код построчно: default_args наследуются всеми задачами. schedule="*/15 * * * *" — это cron. catchup=False — не запускать пропущенные периоды. Оператор >> задаёт зависимость.

Групповое задание

Спроектируйте архитектуру пайплайна для ТЧЭ-15 (15 минут):

Разделитесь на 3 группы. Каждая группа проектирует один пайплайн:
  • Группа 1 — Телеметрия: источники (ГЛОНАСС, датчики букс), периодичность (15 мин), шаги обработки, целевые таблицы в rzd_analytics, алерты при перегреве букс.
