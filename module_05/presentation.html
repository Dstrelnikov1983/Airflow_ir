Зависимости задач — зачем они нужны?

Без зависимостей задачи выполняются хаотично и одновременно. Это приводит к:

  • Обработке данных до их появления
  • Гонкам состояний (race conditions)
  • Некорректным агрегатам и KPI
  • Сложной отладке сбоев
Пример: нельзя считать агрегат до того, как загружены все исходные данные из источников.

Граф зависимостей DAG (DAG — Directed Acyclic Graph)

collect_data
↓
parse_source_a
parse_source_b
↓
merge_data
↓
calculate_kpi
↓
notify
Ключевое свойство DAG: рёбра графа определяют порядок и условия запуска задач. Airflow Scheduler читает граф и ставит задачи в очередь только тогда, когда все их upstream-задачи завершились успешно.

Синтаксис зависимостей

Способ 1: операторы >> и <<

from airflow import DAG
from airflow.operators.python import PythonOperator

# a запускается ПЕРЕД b
task_a >> task_b

# b запускается ПЕРЕД a (то же самое)
task_b << task_a

# Цепочка: a → b → c
task_a >> task_b >> task_c

# Параллельный fan-out: a → b и a → c
task_a >> [task_b, task_c]

# Fan-in: b и c должны завершиться → d
[task_b, task_c] >> task_d

Способ 2: методы set_upstream / set_downstream

# set_downstream — то же что >>
task_a.set_downstream(task_b)

# set_upstream — то же что <<
task_b.set_upstream(task_a)

# Множественные зависимости
task_a.set_downstream([task_b, task_c])
[task_b, task_c].set_downstream(task_d)

# cross_downstream — матрица зависимостей
from airflow.models.baseoperator import cross_downstream

cross_downstream(
    from_tasks=[task_a, task_b],
    to_tasks=[task_c, task_d]
)
Рекомендация: используйте оператор >> — он нагляднее отражает направление потока данных. Методы set_upstream/set_downstream удобны при динамическом построении DAG в цикле.

Паттерны зависимостей

1. Линейный (Sequential)
A
→
B
→
C

Строго последовательно. Каждый шаг ждёт предыдущего.
Пример: collect → validate → load

2. Fan-out (распараллеливание)
Extract

↙   ↘
Src A
Src B

Одна задача порождает несколько параллельных.
Пример: параллельная обработка нескольких источников

3. Fan-in (объединение)
Src A
Src B
↘   ↙
Merge

Несколько задач сходятся в одну.
Пример: объединение данных из нескольких источников

4. Diamond (ромб)
Start

↙   ↘
Branch A
Branch B
↘   ↙
Finish

Fan-out + Fan-in. Наиболее типичен для ETL.
Пример: полный пайплайн расчёта итогового KPI

Сенсоры в Airflow

Что такое сенсор?

Специальный тип оператора, который ждёт наступления внешнего условия прежде чем передать управление следующим задачам.

Как работает:

  1. Сенсор запускается Scheduler-ом
  2. Вызывает метод poke()
  3. Если условие True — завершается успешно
  4. Если False — ждёт poke_interval сек и повторяет
  5. При превышении timeout — задача падает с ошибкой

Ждёт появления файла
⏰

Ждёт наступления времени
🗄️

🔄

FileSensor — ожидание файла

Типовой сценарий: внешняя система выгружает файл data_YYYYMMDD.csv в фиксированное время. Пайплайн должен дождаться его появления.

from airflow.sensors.filesystem import FileSensor

wait_nav_file = FileSensor(
    task_id="wait_navigation_file",
    # Путь к файлу (поддерживает glob)
    filepath="/data/navigation/navigation_{{ ds_nodash }}.csv",
    # Соединение с файловой системой
    fs_conn_id="fs_navigation",
    # Интервал опроса (секунды)
    poke_interval=60,
    # Максимальное время ожидания (секунды)
    timeout=7200,  # 2 часа
    # Режим работы сенсора
    mode="reschedule",
    # Мягкий сбой (не FAILED, а SKIPPED при timeout)
    soft_fail=False,
    dag=dag,
)

Параметры FileSensor

ПараметрОписание
filepathПуть или glob-паттерн
fs_conn_idConnection ID файловой системы
poke_intervalИнтервал проверки (сек)
timeoutМаксимальное ожидание (сек)
modepoke / reschedule
soft_failSKIPPED вместо FAILED
exponential_backoffНарастающий интервал
Совет: используйте шаблоны Jinja ({{ ds_nodash }}) для динамических путей — тогда каждый запуск DAG ждёт свой файл.

TimeSensor и TimeDeltaSensor

TimeSensor — ждать до определённого времени

from airflow.sensors.time_sensor import TimeSensor
from datetime import time

# Ждать до 06:30 — момента завершения
# ночной смены на шахте «Руда+»
wait_shift_end = TimeSensor(
    task_id="wait_night_shift_end",
    target_time=time(6, 30),  # 06:30 UTC
    mode="reschedule",
    dag=dag,
)

TimeDeltaSensor — ждать N времени от execution_date

from airflow.sensors.time_delta import TimeDeltaSensor
from datetime import timedelta

# Ждать 30 минут после старта DAG,
# чтобы данные телеметрии накопились
wait_data_accumulate = TimeDeltaSensor(
    task_id="wait_data_accumulate",
    delta=timedelta(minutes=30),
    mode="reschedule",
    dag=dag,
)
Когда использовать?
  • TimeSensor — когда данные готовы в фиксированное время суток (смена закончилась, выгрузка завершена)
  • TimeDeltaSensor — когда нужно дать системе "отстояться" после старта (накопить данные, дождаться репликации)
Типовой сценарий:
Период учёта закрывается в 20:00. Расчёт KPI запускается в 20:00, но ждёт до 20:15 (TimeDeltaSensor), чтобы все источники успели отправить финальные данные.
Важно: TimeSensor сравнивает со временем текущего execution_date, а не с реальным временем суток. Для реального времени используйте datetime.utcnow() в Python-сенсоре.

SqlSensor — ожидание данных в БД

Задача: пайплайн расчёта показателей должен запуститься только после того, как в таблицу raw_sensor_data поступили данные за текущий период.

from airflow.sensors.sql import SqlSensor

# Ждать появления записей за текущую смену
wait_shift_data = SqlSensor(
    task_id="wait_shift_data_in_db",
    conn_id="postgres_mes",
    sql="""
        SELECT COUNT(*)
        FROM raw_sensor_data
        WHERE shift_date = '{{ ds }}'
          AND shift_num  = {{ var.value.current_shift }}
          AND record_count > 100
    """,
    # Сенсор считает условие выполненным,
    # если запрос вернул ненулевое значение
    success=lambda records: records[0][0] > 0,
    poke_interval=120,   # каждые 2 минуты
    timeout=3600,        # максимум 1 час
    mode="reschedule",
    dag=dag,
)
Параметры SqlSensor
  • conn_id — подключение к БД
  • sql — SQL-запрос (поддерживает Jinja)
  • success — лямбда для проверки результата
  • failure — лямбда для определения сбоя
  • poke_interval — интервал проверки
Типовая схема использования:

wait_shift_data
(SqlSensor)
↓
calculate_oee
↓
send_report

Режимы сенсора: poke vs reschedule

Режим poke (по умолчанию)
  • Задача занимает воркер всё время ожидания
  • Спит poke_interval секунд между проверками
  • Блокирует слот в пуле воркеров
  • Подходит для коротких ожиданий (< 5 минут)
sensor = FileSensor(
    task_id="wait_file",
    filepath="/data/file.csv",
    mode="poke",          # держит воркер
    poke_interval=30,     # проверка каждые 30с
)
Режим reschedule (рекомендуется)
  • Задача освобождает воркер между проверками
  • Scheduler перезапускает сенсор через интервал
  • Экономит ресурсы кластера
  • Подходит для долгих ожиданий (> 5 минут)
sensor = FileSensor(
    task_id="wait_file",
    filepath="/data/file.csv",
    mode="reschedule",    # освобождает воркер
    poke_interval=300,    # проверка каждые 5 мин
)
Практическое правило: если ожидаемый файл появляется через десятки минут после старта, используем mode="reschedule" с poke_interval=300 (5 мин) — не тратим воркер попусту. При быстрых HTTP-проверках состояния — mode="poke" с poke_interval=10.

Код: пайплайн «Руда+» с зависимостями

from datetime import datetime, timedelta
from airflow import DAG
from airflow.sensors.filesystem import FileSensor
from airflow.sensors.sql import SqlSensor
from airflow.operators.python import PythonOperator
from airflow.operators.email import EmailOperator

# ── Функции задач ────────────────────────────────────────────────

def merge_nav_and_sensors(**ctx):
    """Объединяет данные навигации и телеметрии датчиков."""
    ds = ctx["ds_nodash"]
    nav_path = f"/data/navigation/navigation_{ds}.csv"
    print(f"[merge] Читаем навигацию: {nav_path}")
    # здесь: pandas merge, запись в staging таблицу
    return {"rows_merged": 15420}

def calc_ore_quality(**ctx):
    """Рассчитывает качественные показатели руды за смену."""
    print("[ore_quality] Fe%=62.4, влажность=4.1%, сера=0.08%")
    return {"fe_pct": 62.4, "moisture": 4.1, "sulfur": 0.08}

def calc_equipment_oee(**ctx):
    """Рассчитывает OEE для всего парка оборудования."""
    availability   = 0.92   # 92% — плановое время работы
    performance    = 0.87   # 87% — скорость vs норматив
    quality        = 0.96   # 96% — годная продукция
    oee = availability * performance * quality
    print(f"[oee] OEE = {oee:.1%}")
    return {"oee": round(oee, 4)}

def generate_shift_report(**ctx):
    """Формирует итоговый PDF-отчёт смены."""
    ti = ctx["ti"]
    ore = ti.xcom_pull(task_ids="calc_ore_quality")
    oee = ti.xcom_pull(task_ids="calc_equipment_oee")
    report = {
        "shift_date": ctx["ds"],
        "ore_quality": ore,
        "equipment_oee": oee,
    }
    print(f"[report] Отчёт сформирован: {report}")
    return report

# ── Параметры DAG ────────────────────────────────────────────────

default_args = {
    "owner": "mes_team",
    "retries": 2,
    "retry_delay": timedelta(minutes=5),
    "email_on_failure": True,
    "email": ["mes-alerts@ruda-plus.ru"],
}

with DAG(
    dag_id="ruda_plus_shift_pipeline",
    description="MES пайплайн обработки данных смены «Руда+»",
    schedule_interval="0 8,20 * * *",   # старт смены в 08:00 и 20:00
    start_date=datetime(2024, 1, 1),
    catchup=False,
    default_args=default_args,
    tags=["ruda_plus", "mes", "shift"],
) as dag:

    # ── ЗАДАЧА 1: Ждём навигационный файл ───────────────────────
    wait_navigation_file = FileSensor(
        task_id="wait_navigation_file",
        filepath="/data/navigation/navigation_{{ ds_nodash }}.csv",
        fs_conn_id="fs_navigation",
        poke_interval=300,
        timeout=7200,
        mode="reschedule",
    )

    # ── ЗАДАЧА 2: Ждём данные телеметрии в БД ───────────────────
    wait_sensor_data = SqlSensor(
        task_id="wait_sensor_data",
        conn_id="postgres_mes",
        sql="""
            SELECT COUNT(*)
            FROM raw_sensor_data
            WHERE record_date = '{{ ds }}'
              AND record_count > 100
        """,
        success=lambda r: r[0][0] > 0,
        poke_interval=120,
        timeout=3600,
        mode="reschedule",
    )

    # ── ЗАДАЧА 3: Объединение данных ─────────────────────────────
    merge_data = PythonOperator(
        task_id="merge_nav_and_sensors",
        python_callable=merge_nav_and_sensors,
    )

    # ── ЗАДАЧА 4: Качество руды (параллельно с OEE) ──────────────
    ore_quality = PythonOperator(
        task_id="calc_ore_quality",
        python_callable=calc_ore_quality,
    )

    # ── ЗАДАЧА 5: OEE оборудования ───────────────────────────────
    equipment_oee = PythonOperator(
        task_id="calc_equipment_oee",
        python_callable=calc_equipment_oee,
    )

    # ── ЗАДАЧА 6: Формирование отчёта ────────────────────────────
    shift_report = PythonOperator(
        task_id="generate_shift_report",
        python_callable=generate_shift_report,
    )

    # ── ЗАДАЧА 7: Уведомление руководителя смены ─────────────────
    notify = EmailOperator(
        task_id="notify_shift_manager",
        to="shift-manager@ruda-plus.ru",
        subject="[Руда+] Отчёт смены {{ ds }}",
        html_content="Отчёт смены сформирован. OEE и качество руды — в приложении.",
    )

    # ── ГРАФ ЗАВИСИМОСТЕЙ ────────────────────────────────────────
    # Fan-in: оба сенсора должны завершиться до merge
    [wait_navigation_file, wait_sensor_data] >> merge_data

    # Fan-out: параллельный расчёт качества и OEE
    merge_data >> [ore_quality, equipment_oee]

    # Fan-in: оба расчёта → отчёт → уведомление
    [ore_quality, equipment_oee] >> shift_report >> notify

Кейс для анализа: задержка навигационных данных

Ситуация: На шахте «Руда+» подземная навигационная система (RFID/WiFi-маяки) формирует файл координат оборудования каждые 30 минут. Однако из-за проблем с каналом связи файл иногда поступает с задержкой до 3 часов.

Пайплайн расчёта OEE должен дождаться этого файла перед объединением данных телеметрии, при этом не блокируя кластер.

Требования к решению:

  • Не блокировать воркер на 3 часа
  • Проверять появление файла каждые 10 минут
  • При отсутствии файла через 3 часа — уведомить диспетчера
  • Корректно обрабатывать несколько параллельных запусков
  • Поддерживать ретрай при ошибке чтения файла

Вопрос для обсуждения 1

Что опаснее: слишком много зависимостей или слишком мало?

Рассмотрите оба сценария применительно к MES-системе «Руда+»:
  • Сценарий А: каждая задача явно ждёт завершения предыдущей — даже там, где это не нужно
  • Сценарий Б: задачи запускаются параллельно без явных зависимостей, полагаясь на "порядок вещей"
Много зависимостей:
  • Пайплайн становится медленным
  • Узкие горлышки вместо параллелизма
  • Избыточное время ожидания для OEE
  • Пример: расчёт Fe% ждёт OEE, хотя они независимы
Мало зависимостей:
  • Расчёт по неполным данным
  • Некорректный OEE за смену
  • Трудно воспроизводимые ошибки
  • Пример: OEE считается до загрузки всей телеметрии

Обсуждение: 5 минут в парах, затем общее обсуждение — 5 минут.

Вопрос для обсуждения 2

В чём разница между FileSensor и ExternalTaskSensor?
Когда каждый из них уместен?

В «Руда+» есть два сценария:
  • Сценарий 1: навигационная система выгружает CSV-файл на сетевой диск — пайплайн ждёт его
  • Сценарий 2: DAG сбора данных телеметрии завершил работу — DAG расчёта OEE должен начать
